Git Version Control & CI/CD Pipeline สำหรับ .NET

เรียนรู้กระบวนการพัฒนาซอฟต์แวร์ระดับมืออาชีพ ตั้งแต่ Git Workflow, Branching Strategy, GitHub Actions Automation, Docker Multi-Stage ไปจนถึง Azure Zero-Downtime Deployment
🎯 ระดับ: ⭐ พื้นฐาน > กลาง
⏱️ เวลาเรียน: ~45 นาที
⚡ รางวัล: +100 XP
🛠️ Git / GitHub Actions / Docker / Azure
💡 เปรียบเทียบให้เห็นภาพ (Analogy) — ระบบ Time Machine & สายการบินขนส่งสินค้าอัตโนมัติ
🎮 Git คืออะไร? ทำไมโปรแกรมเมอร์ทุกคนต้องใช้?

ลองนึกถึงตอนที่คุณเล่นเกม RPG ขนาดใหญ่ — Git คือระบบบันทึกจุดเซฟ (Save Checkpoint) และไทม์แมชชีน (Time Machine):
• หากคุณเขียนโค้ดแล้วระบบพัง คุณสามารถกดย้อนเวลา (git checkout / git revert) กลับไปยังจุดเซฟที่โปรแกรมเคยทำงานสมบูรณ์ได้ทันที
• หากต้องการทดลองฟีเจอร์ใหม่เสี่ยงๆ คุณสามารถแยกมิติไทม์ไลน์คู่ขนาน (git branch) ออกไปทดลองได้โดยไม่กระทบโลกหลัก และเมื่อทำสำเร็จก็รวมมิติกลับเข้ามา (git merge)

🚀 CI/CD Pipeline คืออะไร?

CI/CD คือสายพานโรงงานและสายการบินขนส่งสินค้าอัตโนมัติ (Automated Assembly Line & Freight Flight):
• ในอดีต เวลาจะปล่อยโปรแกรมขึ้นเซิร์ฟเวอร์ โปรแกรมเมอร์ต้องมานั่งคอมไพล์โค้ดในเครื่องตัวเอง แล้วใช้โปรแกรม FTP ลากไฟล์ขึ้นเซิร์ฟเวอร์สดๆ ซึ่งเสี่ยงต่อการที่ "โค้ดในเครื่องฉันรันได้ แต่บนเซิร์ฟเวอร์พัง" (It works on my machine!)
• CI (Continuous Integration): ทันทีที่คุณกดปุ่ม git push หุ่นยนต์ใน Cloud จะหยิบโค้ดไปประกอบร่าง (Build) และทำการตรวจสอบความปลอดภัย ทดสอบรัน Unit Tests นับร้อยข้อโดยอัตโนมัติ ภายในเวลาไม่กี่นาที
• CD (Continuous Deployment): เมื่อการทดสอบผ่านฉลุย 100% หุ่นยนต์จะแพ็กแอปใส่ตู้คอนเทนเนอร์ (Docker) และนำไปปล่อยขึ้น Cloud Server (Azure / AWS) ทันทีโดยที่ระบบไม่หยุดให้บริการแม้แต่วินาทีเดียว (Zero Downtime)

01

Git Workflow ในการทำงานจริง (Real-World Git Workflow)

เข้าใจ 4 พื้นที่จัดเก็บของ Git, วงจรชีวิตของโค้ด และกลยุทธ์การแตกกิ่ง (Branching Strategy)

การใช้งาน Git ในระดับมืออาชีพไม่ได้มีแค่การโยนโค้ดขึ้นเว็บ แต่คือการจัดการสถานะของไฟล์ (File Lifecycle) และการประสานงานร่วมกันของนักพัฒนาหลายคนในทีมโดยไม่ให้โค้ดเกิดการขัดแย้ง (Conflict)

📦 แผนผัง 4 พื้นที่จัดเก็บข้อมูลของ Git (The 4 Stages of Git)

💻
1. Working Directory
พื้นที่ทำงานสด

โฟลเดอร์ไฟล์บนเครื่องคุณที่กำลังเปิดเขียนโค้ดใน VS Code หรือ Visual Studio ไฟล์ที่แก้จะอยู่ในสถานะ Modified

👉 เตรียมส่งด้วย git add
📋
2. Staging Area (Index)
ลานเตรียมแพ็กเกจ

จุดคัดเลือกไฟล์ที่พร้อมจะบันทึกเป็น Checkpoint ช่วยให้เราเลือก Commit เฉพาะส่วนที่เสร็จเรียบร้อยได้

👉 บันทึกจุดเซฟด้วย git commit
💾
3. Local Repository
ประวัติศาสตร์ในเครื่อง (.git)

ฐานข้อมูล Git ที่ซ่อนอยู่ในโฟลเดอร์ .git ในเครื่อง เก็บประวัติ Commit ทั้งหมด แม้ไม่มีเน็ตก็ดูประวัติได้

👉 อัปโหลดขึ้น Cloud ด้วย git push
☁️
4. Remote Repository
คลังส่วนกลางบน Cloud

GitHub / Azure DevOps / GitLab ที่ทีมงานทุกคนใช้แชร์โค้ดร่วมกันและใช้ทริกเกอร์ระบบ CI/CD

👉 ดึงการอัปเดตด้วย git pull

⚡ Interactive Git Command Explorer (คลิกเพื่อดูคำอธิบายและตัวอย่างคำสั่ง)

# 1. การสร้างและดึงโปรเจกต์
git init : สร้าง Git repository ใหม่ในโฟลเดอร์ปัจจุบัน
git clone https://github.com/company/dotnet-api.git : โคลนโปรเจกต์จาก Remote ลงมาที่เครื่อง

ชื่อกิ่ง (Branch Name) วัตถุประสงค์ (Purpose) แตกกิ่งมาจาก (Branch From) รวมกลับไปที่ (Merge Back To)
main / master โค้ดเวอร์ชันเสถียรที่สุดที่กำลังรันจริงบน Production เซิร์ฟเวอร์ (ห้าม Push ตรงเด็ดขาด) - -

feature/* พัฒนาฟีเจอร์ใหม่ เช่น feature/stripe-payment หรือ feature/user-profile develop develop (ผ่าน Pull Request)
bugfix/* / hotfix/* แก้ไขข้อผิดพลาดเร่งด่วน โดยเฉพาะ hotfix ที่แก้ปัญหาบน Production ทันที main หรือ develop ทั้ง main และ develop
🤝 ขั้นตอน Pull Request (PR) & Code Review ในชีวิตจริง

1. พัฒนาฟีเจอร์ในกิ่ง feature/my-feature จนเสร็จ พร้อมเขียน Unit Tests กำกับ
2. Push โค้ดขึ้น GitHub แล้วกด "Open Pull Request" เพื่อขอรวมโค้ดเข้าสู่กิ่ง develop หรือ main
3. ระบบ CI Pipeline จะรัน Build และ Automated Tests ให้โดยอัตโนมัติทันที
4. เพื่อนร่วมทีม (Peer Reviewer) เข้ามาตรวจเช็คความสะอาด ความถูกต้อง และประสิทธิภาพ (Code Review)
5. เมื่อผ่านทั้ง CI และได้รับอนุมัติ (Approved) จาก Reviewer จึงจะสามารถกด Merge ได้อย่างปลอดภัย

🛡️ ข้อควรระวังในการเขียน .gitignore สำหรับโปรเจกต์ .NET

ไฟล์ .gitignore ทำหน้าที่บอก Git ว่า "ไฟล์หรือโฟลเดอร์เหล่านี้ไม่ต้องนำเข้าสู่ระบบ Version Control" หากตั้งค่าไม่ถูกต้อง อาจทำให้ไฟล์ขยะขนาดหลายร้อยเมกะไบต์ หรือแม้แต่ รหัสผ่านฐานข้อมูล (Secret Leaks) หลุดขึ้น Public GitHub จนระบบถูกแฮกได้!

ระบบ CI/CD Pipeline ด้วย GitHub Actions

Continuous Integration (ตรวจเช็คและทดสอบอัตโนมัติ) และ Continuous Deployment (ส่งมอบสู่คลาวด์)

ในยุค Modern Cloud Software การส่งมอบงานต้องรวดเร็วและมีเสถียรภาพสูงสุด CI/CD Pipeline จะเปลี่ยนขั้นตอนที่มนุษย์ต้องทำซ้ำๆ ให้กลายเป็นระบบอัตโนมัติ 100%

🔨

1. Build Automation

คอมไพล์โค้ด .NET อัตโนมัติบน Virtual Machine ใน Cloud ทุกครั้งที่มีการเปิด PR เพื่อตรวจจับไวยากรณ์ผิดพลาดก่อนถึงเซิร์ฟเวอร์

🧪

2. Test Automation

สั่งรัน Unit Tests และ Integration Tests (xUnit/NUnit) ทุกตัว หากมีแม้แต่ 1 Test ที่พัง ระบบจะไม่อนุญาตให้ Merge โค้ด

🚢

3. Zero-Downtime Deploy

สร้าง Docker Container และส่งขึ้น Azure App Service หรือ Kubernetes โดยไม่มี Downtime ผู้ใช้งานไม่สะดุดแม้แต่วินาทีเดียว

📄 ตัวอย่างไฟล์ GitHub Actions Workflow (.github/workflows/dotnet.yml)

GitHub Actions จะอ่านการตั้งค่าจากไฟล์ YAML ที่อยู่ในโฟลเดอร์ .github/workflows/ เสมอ:

📄 .github/workflows/dotnet.yml 
name: .NET 8 Build, Test & Deploy Pipeline

# 1. กำหนดเหตุการณ์ที่จะทริกเกอร์ให้ Pipeline ทำงาน (Event Triggers)
on:
  push:
    branches: [ "main", "develop" ]
  pull_request:
    branches: [ "main" ]

jobs:
  build-and-test:
    name: Build, Test and Package
    runs-on: ubuntu-latest # รันบน Linux Container ชั่วคราวของ GitHub

    steps:
    # ─── Step 1: ดึงซอร์สโค้ดจาก Repository ───
    - name: 📥 Check out repository code
      uses: actions/checkout@v4

    # ─── Step 2: ติดตั้ง .NET 8 SDK ───
    - name: ⚙️ Setup .NET 8 SDK
      uses: actions/setup-dotnet@v4
      with:
        dotnet-version: '8.0.x'

    # ─── Step 3: ดึง NuGet Packages ที่โปรเจกต์ต้องใช้ ───
    - name: 📦 Restore dependencies
      run: dotnet restore

    # ─── Step 4: คอมไพล์โปรเจกต์ในโหมด Release ───
    - name: 🔨 Build project
      run: dotnet build --no-restore --configuration Release

    # ─── Step 5: สั่งรัน Unit Tests ทั้งหมดในโซลูชัน ───
    - name: 🧪 Run Unit Tests with xUnit
      run: dotnet test --no-build --configuration Release --verbosity normal --collect:"XPlat Code Coverage"

    # ─── Step 6: รวมไฟล์ที่พร้อมส่งมอบ (Publish Artifact) ───
    - name: 📦 Publish .NET Web App
      if: github.ref == 'refs/heads/main' && github.event_name == 'push'
      run: dotnet publish -c Release -o ./publish

    # ─── Step 7: Deploy ขึ้น Azure Web App ───
    - name: 🚀 Deploy to Azure Web App
      if: github.ref == 'refs/heads/main' && github.event_name == 'push'
      uses: azure/webapps-deploy@v2
      with:
        app-name: 'my-production-dotnet-api'
        publish-profile: ${{ secrets.AZURE_WEBAPP_PUBLISH_PROFILE }}
        package: ./publish
03

Docker Containerization & Multi-Stage Build สำหรับ .NET

แพ็กแอปพลิเคชัน .NET ลง Container ให้ขนาดเล็ก เบา ปลอดภัย และรันได้ทุกที่ในโลก

Docker ช่วยแก้ปัญหาคลาสสิกของชาวเดฟที่ว่า "บนเครื่องฉันรันได้ แต่บนเซิร์ฟเวอร์รันไม่ได้" เพราะ Docker จะแพ็กทั้งโค้ด, .NET Runtime, ไลบรารี และระบบปฏิบัติการย่อยๆ รวมไว้ในก้อนเดียวที่เรียกว่า Container Image

💡 ทำไมต้องใช้ Multi-Stage Dockerfile? (เทคนิคหัวใจสำคัญของ DevOps)

ในการพัฒนา .NET เราต้องการ .NET SDK (มีคอมไพเลอร์, Roslyn, CLI) ในการ Build โค้ด แต่เมื่อแอปคอมไพล์เสร็จแล้วตอนรันจริง เราต้องการแค่ ASP.NET Runtime เล็กๆ เท่านั้น!

🛠️ Stage 1: Build Stage (SDK Image)

mcr.microsoft.com/dotnet/sdk:8.0

ขนาด ~850 MB - 1 GB
  • ✅ มี C# Compiler (csc), MSBuild, NuGet Package Manager
  • ✅ มี .NET CLI ครบชุดสำหรับ dotnet restore, dotnet build, dotnet publish
  • ❌ ไม่ควรนำไปรันบน Production เพราะไฟล์ใหญ่ โหลดช้า และเสี่ยงต่อช่องโหว่ความปลอดภัย
⚡ Stage 2: Final Runtime Stage (ASP.NET Image)

mcr.microsoft.com/dotnet/aspnet:8.0

~150 MB
  • ✅ มีเฉพาะ Kestrel Web Server และ .NET CoreCLR สำหรับรัน DLL
  • ✅ คัดลอกเฉพาะไฟล์ Binary ที่ Publish แล้วมาจาก Stage 1 (ไม่มี Source Code หลุด!)
  • ✅ ขนาดเล็กลงกว่าเดิมถึง 80%! สตาร์ตแอปติดเร็ว ปลอดภัย และประหยัดค่าแบนด์วิดท์ Cloud

📄 โค้ด Multi-Stage Dockerfile มาตรฐานสำหรับ ASP.NET Core

🐳 Dockerfile (Multi-Stage Build สำหรับ ASP.NET Core Web API) 
# ══════════════════════════════════════════════════════════
# 1. Base Runtime Stage: เตรียมสภาพแวดล้อมสำหรับรันแอป
# ══════════════════════════════════════════════════════════
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS base
WORKDIR /app
EXPOSE 8080
ENV ASPNETCORE_URLS=http://+:8080

# ══════════════════════════════════════════════════════════
# 2. Build Stage: ใช้ SDK ตัวใหญ่ในการคอมไพล์โค้ด
# ══════════════════════════════════════════════════════════
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

# คัดลอกเฉพาะไฟล์ .csproj เข้ามาก่อน เพื่อทำ Docker Layer Cache สำหรับ NuGet
COPY ["MyWebApi.csproj", "./"]
RUN dotnet restore "./MyWebApi.csproj"

# คัดลอกซอร์สโค้ดทั้งหมดเข้ามาคอมไพล์
COPY . .
RUN dotnet build "MyWebApi.csproj" -c Release -o /app/build

# ══════════════════════════════════════════════════════════
# 3. Publish Stage: รวมไฟล์ DLL และ Static assets
# ══════════════════════════════════════════════════════════
FROM build AS publish
RUN dotnet publish "MyWebApi.csproj" -c Release -o /app/publish /p:UseAppHost=false

# ══════════════════════════════════════════════════════════
# 4. Final Production Stage: ดึงเฉพาะผลลัพธ์มาวางใน Runtime เล็ก
# ══════════════════════════════════════════════════════════
FROM base AS final
WORKDIR /app
# คัดลอกเฉพาะโฟลเดอร์ publish จาก Stage ที่ 3 เข้ามา
COPY --from=publish /app/publish .
ENTRYPOINT ["dotnet", "MyWebApi.dll"]

Cloud Deployment & Azure App Service เบื้องต้น

เข้าใจสถาปัตยกรรมคลาวด์, การทำ Blue-Green Deployment ด้วย Slots และการจัดการ Configuration

เมื่อโปรเจกต์ .NET ผ่านขั้นตอน CI/CD และ Docker เรียบร้อย ขั้นตอนสุดท้ายคือการนำไปเปิดให้บริการบน Cloud Platform เช่น Microsoft Azure หรือ AWS

PaaS (แนะนำสำหรับ Web/API)

Azure App Service

โยนโค้ดหรือ Container ขึ้นไป ระบบ Cloud จัดการ OS Patching, SSL Certificate, Auto-scaling และ Load Balancer ให้เสร็จสรรพ

Microservices & Scale

Azure Container Apps / AKS

IaaS (ควบคุมละเอียด)

Virtual Machines (VM)

🔑 การตั้งค่า Environment Variables และ Connection Strings บน Cloud

ใน ASP.NET Core เมื่อรันบน Cloud ตัวระบบ Configuration Provider จะอ่านค่าจาก Environment Variables โดยอัตโนมัติ โดยใช้เครื่องหมายขีดล่างคู่ (__) แทนเครื่องหมายโคลอน (:) ใน JSON:

⚙️ การแมป Environment Variable บน Cloud สู่ ASP.NET Core C# 
// 1. ใน Azure App Service -> Configuration -> Application Settings ตั้งค่า:
// Key: ConnectionStrings__DefaultConnection
// Value: Server=tcp:sql-prod.database.windows.net;Database=SalesDb;User ID=appadmin;Password=Secret123!;

// 2. ในโค้ด Program.cs ของ .NET 8 จะอ่านค่าได้โดยอัตโนมัติอย่างราบรื่น:
var builder = WebApplication.CreateBuilder(args);

var connectionString = builder.Configuration.GetConnectionString("DefaultConnection");

builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
