Middleware & Request Pipeline

เจาะลึกกลไกสายพานลำเลียงคำขอ HTTP Request Pipeline ใน ASP.NET Core, กฎการเรียงลำดับ Built-in Middleware และการสร้าง Custom Middleware สไตล์โปรดักชัน
🎯 ระดับ: ⭐⭐ กลาง
⏱️ เวลาเรียน: ~40 นาที
⚡ รางวัล: +100 XP
💻 รองรับ .NET 8 / C# 12
🛫
เปรียบเทียบให้เห็นภาพ: ด่านตรวจคนเข้าเมืองและสนามบินนานาชาติ (Airport Security Checkpoints)
ทำความเข้าใจการทำงานแบบ Two-Way Russian Doll Pipeline ผ่านโมเดลผู้โดยสารเครื่องบิน
💡 Analogy: การเดินทางของ HTTP Request เปรียบเสมือนผู้โดยสารในสนามบิน

ลองจินตนาการว่า HTTP Request คือ "ผู้โดยสารเครื่องบิน" ที่ต้องการเดินทางไปถึง "เครื่องบิน (Endpoint / Controller Action)" เพื่อทำภารกิจ ผู้โดยสารไม่สามารถเดินตรงดิ่งขึ้นเครื่องได้ทันที แต่ต้องเดินผ่าน "ด่านตรวจคัดกรองตามลำดับ" (Middleware Pipeline) ทีละด่าน:

Checkpoint 01
🧯 ด่านกู้ภัย & ประกันภัย
app.UseExceptionHandler()
คอยเฝ้าระวังเหตุด่วนเหตุร้าย หากเกิดความผิดพลาดใดๆ ตลอดการเดินทาง ด่านนี้จะเข้าควบคุมสถานการณ์และแจ้งผู้โดยสารอย่างสุภาพ
Checkpoint 02
🔒 ทางเดินเข้าระบบความปลอดภัย
app.UseHttpsRedirection()
บังคับให้ผู้โดยสารทุกคนเดินผ่านช่องทางปลอดภัยที่มีเกราะกำบัง (HTTPS) ไม่อนุญาตให้ใช้ทางเปิดโล่งธรรมดา (HTTP)
Checkpoint 03
🗺️ ป้ายบอกทางไปยัง Gate
app.UseRouting()
จับคู่ตั๋วเดินทางของผู้โดยสารกับ Gate ปลายทาง เพื่อให้ด่านถัดไปรู้ว่าผู้โดยสารคนนี้กำลังจะมุ่งหน้าไปที่ประตูขึ้นเครื่องไหน
Checkpoint 04
🌐 ด่านตรวจพันธมิตรสายการบิน
app.UseCors()
ตรวจสอบว่าผู้โดยสารเดินทางมาจากเว็บไซต์หรือโดเมนที่ได้รับอนุญาตให้เชื่อมต่อกับสนามบินแห่งนี้หรือไม่ (Cross-Origin)
Checkpoint 05
🛂 ด่านตรวจหนังสือเดินทาง (Passport)
app.UseAuthentication()
ตรวจสอบตัวตนว่า "คุณคือใคร?" โดยการอ่าน JWT Token หรือ Cookie ประจำตัวผู้โดยสาร
Checkpoint 06
🎫 ด่านตรวจสิทธิ์ขึ้นเครื่อง (Boarding Pass)
app.UseAuthorization()
ตรวจสอบว่า "คุณมีสิทธิ์เข้า Gate นี้ไหม?" เช่น ตั๋ว Economy จะถูกปฏิเสธไม่ให้เข้าเลานจ์ VIP (403 Forbidden)
⚡ จุดสำคัญที่ต้องจดจำ: การ Short-Circuiting และขากลับ (Response Outbound)
  • การ Short-circuit (ปฏิเสธส่งกลับทันที): หากผู้โดยสารไม่ผ่านด่านตรวจ Passport หรือไม่มีสิทธิ์ ด่าน Middleware นั้นจะสร้าง Response ส่งกลับทันที (เช่น 401 Unauthorized หรือ 403 Forbidden) โดยไม่ส่งต่อไปยังด่านถัดไป และไม่เรียก Endpoint
  • ขากลับ (Two-way Pipeline): เมื่อ Endpoint รันเสร็จและสร้าง Response ข้อมูลจะไหลย้อนกลับผ่าน Middleware เดิมในทิศทางย้อนกลับ (เช่น ดักจับเวลาประมวลผล, บีบอัดข้อมูล GZip, หรือแทรก Security Headers ก่อนส่งถึงมือ Client)
01

สถาปัตยกรรม Request Pipeline & ลำดับการทำงาน

ทำความเข้าใจโครงสร้าง Matryoshka (ตุ๊กตาแม่ลูกดก) และเหตุผลที่ลำดับของ Middleware มีผลชี้ขาดต่อความปลอดภัย

ใน ASP.NET Core ลำดับการลงทะเบียน Middleware ในไฟล์ Program.cs มีความสำคัญสูงสุด เพราะ Middleware แต่ละตัวจะถูกเรียกทำงานเรียงตามลำดับจากบนลงล่างในขาเข้า (Inbound Request) และไหลย้อนกลับจากล่างขึ้นบนในขาออก (Outbound Response)

📋 กฎเหล็ก 5 ประการในการจัดลำดับ Middleware

1
app.UseExceptionHandler() / UseDeveloperExceptionPage()
ต้องอยู่อันดับ 1 บนสุดเสมอ เพื่อให้บล็อก try-catch ภายในครอบคลุม Middleware ทุกตัวและ Endpoint ทั้งหมด
Critical Top
2
app.UseHttpsRedirection() & app.UseHsts()
ควรอยู่ลำดับต้นๆ เพื่อเปลี่ยน HTTP ธรรมดาเป็น HTTPS ทันที ก่อนส่งข้อมูลสำคัญไปยัง Middleware ถัดไป
Security
3
app.UseStaticFiles()
ควรอยู่ก่อน Routing และ Auth เพื่อให้ Request ที่ขอไฟล์ .css, .js, .png สามารถส่งไฟล์กลับได้ทันทีโดยไม่ต้องผ่าน Logic คำนวณความปลอดภัยที่สิ้นเปลือง CPU
Performance
4
app.UseRouting()
ทำหน้าที่วิเคราะห์ URL และเลือก Endpoint ปลายทาง — ต้องอยู่ก่อน CORS, Authentication และ Authorization เพื่อให้ Middleware เหล่านั้นอ่าน Metadata เช่น [Authorize] ได้
Routing
5
app.UseAuthentication() ➔ app.UseAuthorization()
กฎทอง: Authentication ต้องมาก่อน Authorization เสมอ! เพราะต้องระบุว่า "เขาคือใคร" ให้สำเร็จก่อน จึงจะตรวจสิทธิ์ได้ว่า "เขามีสิทธิ์ทำสิ่งนี้หรือไม่"
Auth Pair
⚠️ ข้อผิดพลาดร้ายแรงที่พบบ่อย (Common Pitfall)

หากคุณวาง app.UseAuthorization() ไว้ก่อน app.UseAuthentication() ตัวระบบจะตรวจสิทธิ์บน HttpContext.User ที่ยังว่างเปล่า (Anonymous) เสมอ ทำให้ API ทั้งหมดถูกปฏิเสธด้วยสถานะ 401 Unauthorized แม้ว่า Client จะแนบ JWT Token มาถูกต้องก็ตาม!

02

Built-in Middlewares สำคัญใน ASP.NET Core

ศึกษารายละเอียด หน้าที่ และการใช้งาน Middleware พื้นฐานที่มาพร้อมกับ .NET 8

ASP.NET Core เตรียม Built-in Middleware สำหรับงานสถาปัตยกรรมเว็บมาตรฐานมาให้อย่างครบถ้วน ดังตารางสรุปด้านล่างนี้:

Extension Method หน้าที่หลัก (Responsibilities) Package / Namespace ตำแหน่งใน Pipeline
app.UseExceptionHandler() ดักจับ Unhandled Exceptions ทั้งหมดในระบบ แล้วแปลงเป็น ProblemDetails หรือแสดง Error Page Microsoft.AspNetCore.Diagnostics บนสุด (อันดับ 1)
app.UseHttpsRedirection() Redirect ทุกคำขอที่ไม่ปลอดภัย (HTTP) ไปยัง HTTPS (พอร์ต 443/5001) ด้วยรหัส 307 หรือ 308 Microsoft.AspNetCore.HttpsPolicy อันดับ 2
app.UseStaticFiles() ให้บริการไฟล์ Static จากโฟลเดอร์ wwwroot เช่น รูปภาพ, CSS, JS, HTML โดยไม่ต้องผ่าน Controller Microsoft.AspNetCore.StaticFiles ก่อน Routing
app.UseRouting() จับคู่ HTTP Request กับ Route Template และแนบ Endpoint Metadata ลงใน HttpContext Microsoft.AspNetCore.Routing ก่อน CORS & Auth
app.UseCors("PolicyName") ตั้งค่า Cross-Origin Resource Sharing เพื่ออนุญาตให้ Single Page App (React, Vue, Angular) เรียกใช้งาน API ข้ามโดเมนได้ Microsoft.AspNetCore.Cors หลัง Routing
app.UseAuthentication() อ่าน Credentials (JWT Bearer, Cookies, API Key) แล้วสร้าง ClaimsPrincipal บรรจุใน HttpContext.User Microsoft.AspNetCore.Authentication ก่อน Authorization
app.UseAuthorization() ตรวจสอบ Roles, Claims, และ Authorization Policies ว่าผู้ใช้มีสิทธิ์เข้าถึง Endpoint นั้นๆ หรือไม่ Microsoft.AspNetCore.Authorization หลัง Authentication
app.UseSwagger()
app.UseSwaggerUI()		 สร้างเอกสาร OpenAPI JSON Specification และหน้าเว็บ Swagger UI สำหรับทดสอบ API (มักใช้เฉพาะใน Development Environment) Swashbuckle.AspNetCore ใน if (IsDev)

💻 ตัวอย่างไฟล์ Program.cs ฉบับมาตรฐานสมบูรณ์ (.NET 8 Minimal API)

โครงสร้างการจัดวาง Middleware ในลำดับที่ถูกต้องตาม Best Practice ของ Microsoft:

📄 Program.cs — Standard ASP.NET Core Request Pipeline 
var builder = WebApplication.CreateBuilder(args);

// ─────────────────────────────────────────────────────────────
// 1. DI SERVICE REGISTRATION (กำหนดบริการลงใน IoC Container)
// ─────────────────────────────────────────────────────────────
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

// ลงทะเบียน CORS Policy
builder.Services.AddCors(options =>
{
    options.AddPolicy("AllowFrontendApp", policy =>
    {
        policy.WithOrigins("https://localhost:3000", "https://myapp.com")
              .AllowAnyHeader()
              .AllowAnyMethod();
    });
});

// ลงทะเบียน Authentication & Authorization
builder.Services.AddAuthentication("Bearer")
    .AddJwtBearer();
builder.Services.AddAuthorization();

var app = builder.Build();

// ─────────────────────────────────────────────────────────────
// 2. HTTP REQUEST PIPELINE (จัดลำดับ Middleware ขาเข้า-ขาออก)
// ─────────────────────────────────────────────────────────────

// [1] Exception Handling: ดักจับ Error ทั่วทั้งระบบ
if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
    app.UseDeveloperExceptionPage(); // แสดงหน้ารายละเอียด Error สำหรับ Dev
}
else
{
    app.UseExceptionHandler("/error"); // ส่งไปที่ Error Endpoint กลางใน Production
    app.UseHsts(); // บังคับเบราว์เซอร์ใช้ HTTPS อย่างเข้มงวด
}

// [2] HTTPS Redirection: บังคับเชื่อมต่อแบบปลอดภัย
app.UseHttpsRedirection();

// [3] Static Files: ส่งไฟล์ wwwroot โดยไม่ต้องคำนวณ Route
app.UseStaticFiles();

// [4] Routing: จับคู่ Request กับ Route Template
app.UseRouting();

// [5] CORS: จัดการความปลอดภัยข้ามโดเมน (ต้องอยู่หลัง UseRouting เสมอ)
app.UseCors("AllowFrontendApp");

// [6] Authentication: แกะ Token ยืนยันตัวตน ("คุณคือใคร?")
app.UseAuthentication();

// [7] Authorization: ตรวจสอบสิทธิ์การเข้าถึง ("คุณทำได้ไหม?")
app.UseAuthorization();

// ─────────────────────────────────────────────────────────────
// 3. ENDPOINTS EXECUTION (ประมวลผลคำสั่งตาม Business Logic)
// ─────────────────────────────────────────────────────────────
app.MapGet("/api/profile", (HttpContext context) =>
{
    var username = context.User.Identity?.Name ?? "Guest";
    return Results.Ok(new { Message = $"สวัสดีคุณ {username}", ServerTime = DateTime.UtcNow });
}).RequireAuthorization(); // บังคับว่าต้องผ่าน Authorization ก่อน

app.Run();

การเขียน Custom Middleware ระดับโปรดักชัน

สร้าง Middleware ขึ้นมาใช้เองเพื่อดักจับ Performance, ตรวจสอบ Header, และจัดการ Global Error

ใน ASP.NET Core เราสามารถสร้าง Custom Middleware ได้ 2 วิธีหลัก คือ Inline Middleware (เหมาะกับงานเล็กๆ ไม่ซับซ้อน) และ Class-Based Middleware (แนะนำสำหรับ Production เพราะโค้ดเป็นระเบียบ Test ได้ง่าย และ Reuse ซ้ำได้)

วิธีที่ 1: Inline Middleware ด้วย app.Use()

ใช้ Lambda Function รับพารามิเตอร์ HttpContext context และ RequestDelegate next:

⚡Program.cs — Inline Logging Middleware
app.Use(async (HttpContext context, RequestDelegate next) =>
{
    // 1. โค้ดส่วนนี้จะทำงานใน "ขาเข้า" (Inbound Request)
    Console.WriteLine($"[INBOUND] 👉 {context.Request.Method} {context.Request.Path}");

    // 2. เรียก next(context) เพื่อส่งต่อการทำงานไปยัง Middleware ตัวถัดไปใน Pipeline
    await next(context);

    // 3. โค้ดส่วนนี้จะทำงานใน "ขาออก" (Outbound Response) หลัง Endpoint ทำงานเสร็จ
    Console.WriteLine($"[OUTBOUND] 👈 Response Status Code: {context.Response.StatusCode}");
});

วิธีที่ 2: Class-based Middleware (มาตรฐาน Production)

การเขียนแบบแยกคลาสจะประกอบด้วย Constructor ที่รับ RequestDelegate _next และเมธอด public async Task InvokeAsync(HttpContext context):

⏱️
ตัวอย่างจริงที่ 1: Request Timing & Performance Logging Middleware
บันทึกเวลาประมวลผลของทุก Request, แนบ Header X-Response-Time-ms, และแจ้งเตือนเมื่อ Request ช้าเกินไป
🛡️Middlewares/RequestPerformanceMiddleware.cs
using System.Diagnostics;

namespace DotNetHub.Api.Middlewares;

public class RequestPerformanceMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestPerformanceMiddleware> _logger;

    public RequestPerformanceMiddleware(RequestDelegate next, ILogger<RequestPerformanceMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        // 1. เริ่มจับเวลาด้วย Stopwatch ในขาเข้า
        var stopwatch = Stopwatch.StartNew();

        // ดักจับ Header ขาออกเพื่อแนบ Response Time Header
        context.Response.OnStarting(() =>
        {
            stopwatch.Stop();
            var elapsedMs = stopwatch.ElapsedMilliseconds;
            context.Response.Headers["X-Response-Time-ms"] = elapsedMs.ToString();
            return Task.CompletedTask;
        });

        // 2. ส่งต่อให้ Middleware ตัวถัดไปทำงาน
        await _next(context);

        // 3. ตรวจสอบในขาออก: หากทำงานช้าเกิน 500ms ให้ส่ง Warning Log
        if (stopwatch.ElapsedMilliseconds > 500)
        {
            _logger.LogWarning("⚠️ Slow Request: {Method} {Path} ใช้เวลา {Elapsed} ms!",
                context.Request.Method,
                context.Request.Path,
                stopwatch.ElapsedMilliseconds);
        }
        else
        {
            _logger.LogInformation("✅ Completed: {Method} {Path} ใน {Elapsed} ms [Status: {StatusCode}]",
                context.Request.Method,
                context.Request.Path,
                stopwatch.ElapsedMilliseconds,
                context.Response.StatusCode);
        }
    }
}

// Extension Method เพื่อความ Clean ในการเรียกใช้ที่ Program.cs
public static class RequestPerformanceMiddlewareExtensions
{
    public static IApplicationBuilder UseRequestPerformanceLogger(this IApplicationBuilder app)
    {
        return app.UseMiddleware<RequestPerformanceMiddleware>();
    }
}
🚨
ตัวอย่างจริงที่ 2: Global Exception Handling Middleware (RFC 7807)
ดักจับ Exception ทั่วทั้ง Application แล้วแปลงเป็นโครงสร้าง JSON มาตรฐาน ProblemDetails พร้อมส่ง HTTP Status Code ที่ถูกต้อง
🛡️Middlewares/GlobalExceptionHandlerMiddleware.cs
using System.Net;
using System.Text.Json;

namespace DotNetHub.Api.Middlewares;

public class GlobalExceptionHandlerMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<GlobalExceptionHandlerMiddleware> _logger;

    public GlobalExceptionHandlerMiddleware(RequestDelegate next, ILogger<GlobalExceptionHandlerMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            // พยายามส่งต่อการทำงานตามปกติ
            await _next(context);
        }
        catch (Exception ex)
        {
            // ดักจับ Error ที่หลุดออกมาจาก Controller / Service ทั้งหมด
            _logger.LogError(ex, "❌ Unhandled Exception เกิดข้อผิดพลาดขึ้นในระบบ: {Message}", ex.Message);
            await HandleExceptionAsync(context, ex);
        }
    }

    private static async Task HandleExceptionAsync(HttpContext context, Exception exception)
    {
        context.Response.ContentType = "application/problem+json";

        var statusCode = exception switch
        {
            KeyNotFoundException => HttpStatusCode.NotFound,             // 404
            UnauthorizedAccessException => HttpStatusCode.Unauthorized, // 401
            ArgumentException => HttpStatusCode.BadRequest,              // 400
            _ => HttpStatusCode.InternalServerError                     // 500
        };

        context.Response.StatusCode = (int)statusCode;

        var errorResponse = new
        {
            Status = (int)statusCode,
            Title = exception.GetType().Name,
            Detail = exception.Message,
            Instance = context.Request.Path.Value,
            Timestamp = DateTime.UtcNow
        };

        var jsonOptions = new JsonSerializerOptions { PropertyNamingPolicy = JsonNamingPolicy.CamelCase };
        var jsonResponse = JsonSerializer.Serialize(errorResponse, jsonOptions);

        await context.Response.WriteAsync(jsonResponse);
    }
}

// Extension Method
public static class GlobalExceptionHandlerExtensions
{
    public static IApplicationBuilder UseGlobalExceptionHandler(this IApplicationBuilder app)
    {
        return app.UseMiddleware<GlobalExceptionHandlerMiddleware>();
    }
}
💡 วิธีเรียกใช้งานใน Program.cs แบบสวยงาม (Clean Syntax)
var app = builder.Build();
app.UseGlobalExceptionHandler(); // ใส่ไว้บนสุดเพื่อดัก Exception ทั้งหมด
app.UseRequestPerformanceLogger(); // จับเวลาทุก Request
04

เปรียบเทียบ app.Use(), app.Run(), app.Map()

ความแตกต่างระหว่าง Chaining, Terminal และ Branching Middleware

ในการประกอบ Pipeline เรามี 3 เมธอดหลักในการผูก Middleware เข้าสู่ระบบ ซึ่งแต่ละตัวมีพฤติกรรมและหน้าที่แตกต่างกันอย่างชัดเจน:

app.Use()
🔗 Chaining Middleware

ทำหน้าที่ประมวลผลคำขอ แล้วสามารถส่งต่อไปยัง Middleware ถัดไปได้โดยการเรียก await next(context) และกลับมาทำงานต่อในขากลับได้ 

app.Use(async (context, next) =>
{
    // Do work before
    await next(context); // ส่งต่อ
    // Do work after
});
app.Run()
🛑 Terminal Middleware

ทำหน้าที่เป็นจุดสิ้นสุดของท่อส่ง (Terminal) จะไม่มีพารามิเตอร์ next เมื่อทำงานเสร็จจะส่ง Response กลับทันที และไม่มี Middleware ด้านล่างถูกทำงานต่อ 

app.Run(async (context) =>
{
    // จบการทำงาน ส่งผลลัพธ์ทันที
    await context.Response
        .WriteAsync("Terminal Point!");
});
app.Map() / MapWhen()
🌿 Branching Middleware

ทำหน้าที่แตกแขนงท่อส่ง (Branch Pipeline) ออกเป็นเส้นทางใหม่ตาม URL Path (เช่น /admin) หรือตามเงื่อนไข Predicate ใน Request Headers 

app.Map("/admin", adminApp =>
{
    adminApp.Use(async (ctx, next) => {
        // Pipeline เฉพาะของ /admin
        await next(ctx);
    });
    adminApp.Run(async ctx => {
        await ctx.Response.WriteAsync("Admin Area");
    });
});

📊 ตารางสรุปคุณสมบัติ (Comparison Matrix)

คุณสมบัติ (Feature) app.Use() app.Run() app.Map() / MapWhen()
ประเภท (Category) Chaining (ต่อท่อส่งต่อ) Terminal (ปลายทางท่อ) Branching (แตกกิ่งก้านสาขา)
มีพารามิเตอร์ next หรือไม่? มี (ส่งต่อได้) ไม่มี (สิ้นสุดทันที) มี Sub-pipeline เฉพาะ
Short-circuit ได้หรือไม่? ทำได้ (หากไม่เรียก await next()) เป็นธรรมชาติของตัวมันเอง ทำได้ภายใน Sub-pipeline
Use Cases ที่เหมาะสม Logging, CORS, Auth, Header Injection, Error Handling หน้า Fallback, Health Check แบบ Simple, Static Response แยก Pipeline พิเศษสำหรับ /webhooks, /internal, /admin
