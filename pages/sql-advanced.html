📖 ปริศนาที่ 1: สารบัญท้ายเล่มหนังสือ (Database Indexing)

ลองนึกภาพหนังสือสารานุกรมหนา 1,000,000 หน้า หากคุณต้องการหาคำว่า "Quantum Computing" แต่หนังสือเล่มนี้ไม่มีสารบัญหรือดัชนีท้ายเล่ม คุณมีทางเลือกเดียวคือ เปิดอ่านทีละหน้าตั้งแต่หน้า 1 ไปจนถึงหน้าสุดท้าย (นี่คือสิ่งที่ฐานข้อมูลเรียกว่า Table Scan ใช้เวลาค้นหานานมาก O(N))

แต่ถ้าหนังสือมี ดัชนีท้ายเล่ม (Index) ที่เรียงตามอักษร A-Z คุณจะเปิดไปที่หมวดอักษร Q แล้วพบว่า "Quantum Computing อยู่หน้า 742" จากนั้นคุณพลิกตรงไปยังหน้า 742 ได้ในเวลาเพียง เสี้ยววินาที! (นี่คือสิ่งที่ฐานข้อมูลเรียกว่า Index Seek บนโครงสร้าง B-Tree ที่มีความเร็วระดับ O(log N))

🏦 ปริศนาที่ 2: การทำสัญญาโอนเงินธนาคาร (Transactions & ACID)

การโอนเงิน 10,000 บาทจาก นาย A ไปให้ นาย B ในโลกของฐานข้อมูลประกอบด้วย 2 ขั้นตอนแยกกัน:
1. UPDATE Accounts SET Balance = Balance - 10000 WHERE User = 'A';
2. UPDATE Accounts SET Balance = Balance + 10000 WHERE User = 'B';

สมมติว่าขั้นตอนที่ 1 สำเร็จ (ตัดเงิน A ไปแล้ว) แต่ทันใดนั้นเกิดไฟดับ เซิร์ฟเวอร์ล่ม หรือเน็ตตัดก่อนที่ขั้นตอนที่ 2 จะทำงาน! เงิน 10,000 บาทจะหายวับไปกับตา!

Database Transaction คือกลไกสัญญา "สำเร็จครบทั้งหมด (COMMIT) หรือถ้าพังแม้แต่นิดเดียวให้ย้อนคืนสู่จุดเริ่มต้น (ROLLBACK)" เพื่อรับประกันว่าเงินจะไม่สูญหายและข้อมูลจะถูกต้องสมบูรณ์แบบ 100% เสมอ

01 Database Indexing — ผ่าโครงสร้าง B-Tree และเบื้องหลังความเร็ว

Index ในฐานข้อมูลเชิงสัมพันธ์ (RDBMS เช่น SQL Server, PostgreSQL, MySQL) คือโครงสร้างข้อมูลพิเศษที่สร้างขึ้นเพื่อเพิ่มความเร็วในการค้นหาแถวข้อมูล (Retrieve Rows) โดยใช้โครงสร้างแบบ B-Tree (Balanced Tree)

เปรียบเทียบ Clustered Index vs Non-Clustered Index

หัวข้อเปรียบเทียบ 🔴 Clustered Index 🔵 Non-Clustered Index
การจัดเก็บทางกายภาพ (Physical Order) จัดเรียงข้อมูลแถวจริงบน Hard Disk / SSD ตามลำดับของ Index Key สร้างโครงสร้าง B-Tree แยกต่างหาก โดย Leaf Node จะเก็บ Key และตัวชี้ (Pointer / Bookmark) ไปยังแถวจริง
จำนวนต่อ 1 ตาราง มีได้เพียง 1 ตัวเท่านั้น ต่อ 1 ตาราง (เพราะข้อมูลจริงจัดเรียงลำดับกายภาพได้แบบเดียว) สร้างได้หลายตัว (ใน SQL Server สร้างได้สูงสุดถึง 999 ตัวต่อตาราง)
ค่าเริ่มต้น (Default) ระบบจะสร้างให้อัตโนมัติเมื่อกำหนด PRIMARY KEY ให้ตาราง สร้างเพิ่มเติมเองตามคอลัมน์ที่ถูกค้นหาบ่อยๆ เช่น Email, CitizenId, CreatedDate
Leaf Node เก็บอะไร? Data Pages จริง ครบทุกคอลัมน์ของแถวนั้น (ไม่ต้องค้นต่อ) Index Key + Clustered Key (หรือ Heap RID) เพื่อใช้ทำ Key Lookup
ตัวอย่างการสร้าง CREATE CLUSTERED INDEX IX_Users_Id ON Users(UserId); CREATE NONCLUSTERED INDEX IX_Users_Email ON Users(Email);

ศัพท์สำคัญใน Execution Plan: Scan vs Seek

❌
Table Scan (Heap Scan)
ความเร็ว: O(N) — ช้าที่สุด
ตารางไม่มี Clustered Index และไม่มี Index ที่ตรงกับเงื่อนไข Database Engine จึงต้องอ่านข้อมูลทุกหน้าดิสก์ตั้งแต่แถวแรกยันแถวสุดท้าย เปลือง I/O สูงมาก
⚠️
Index Scan
ความเร็ว: O(N ของ Index) — ปานกลาง
มี Index อยู่ แต่เงื่อนไข WHERE ไม่สามารถกระโดดเจาะจงได้ (เช่น WHERE LastName LIKE '%son') Database Engine จึงต้องกวาดอ่านทุกหน้าใน Leaf Level ของ Index
⚡
Index Seek
ความเร็ว: O(log N) — เร็วที่สุด ยอดเยี่ยม!
Database Engine ใช้คุณสมบัติ B-Tree วิ่งจาก Root Node ตรงดิ่งลงไปยัง Leaf Page ที่ตรงกับเงื่อนไขทันที อ่านหน้าดิสก์เพียง 3-4 หน้า แม้ตารางจะมีข้อมูลเป็นร้อยล้านแถว!

Covering Index & INCLUDE Columns (เทคนิคระดับ Advance)

เมื่อ Query มีการค้นหาด้วย Non-Clustered Index แต่ต้องการ SELECT คอลัมน์อื่นๆ ที่ไม่ได้อยู่ใน Index ด้วย Database Engine จะต้องทำ Key Lookup (Bookmark Lookup) ย้อนกลับไปค้นข้อมูลจริงที่ Clustered Index ซึ่งหากผลลัพธ์มีหลายแถวจะทำให้ช้าลงอย่างมาก

📜 Covering-Index-Optimization.sql 
-- สมมติมี Query ที่ระบบ API เรียกใช้งานบ่อยมาก:
SELECT FirstName, LastName, Email, PhoneNumber 
FROM Customers 
WHERE CitizenId = '1234567890123';

-- ❌ แบบที่ 1: สร้าง Index ปกติ (เกิด Key Lookup ไปยัง Clustered Index เพื่อเอา Phone, Name)
CREATE NONCLUSTERED INDEX IX_Customers_CitizenId 
ON Customers(CitizenId);

-- ✅ แบบที่ 2: สร้าง Covering Index ด้วย INCLUDE (เร็วกว่ามหาศาล ไม่มี Key Lookup!)
-- CitizenId จะอยู่ในโครงสร้าง B-Tree สำหรับค้นหา (Seek)
-- ส่วนคอลัมน์ใน INCLUDE จะถูกเก็บไว้ที่ Leaf Level ไม่เปลืองขนาดของ Tree Node
CREATE NONCLUSTERED INDEX IX_Customers_CitizenId_Covering 
ON Customers(CitizenId)
INCLUDE (FirstName, LastName, Email, PhoneNumber);

⚠️ เมื่อไหร่ที่ Index อาจทำให้ระบบช้าลง? (The Cost of Over-Indexing)
  • Write Overhead (INSERT, UPDATE, DELETE ช้าลง): ทุกครั้งที่เขียนข้อมูลใหม่ ฐานข้อมูลจะต้องตามไปปรับโครงสร้างและจัดสมดุล B-Tree ของทุก Index ที่เกี่ยวข้อง
  • Disk & RAM Bloat: หากสร้าง Index มากเกินไป ขนาดไฟล์ Index อาจใหญ่กว่าข้อมูลจริงในตาราง และแย่งพื้นที่ RAM Buffer Pool ของเซิร์ฟเวอร์
  • Page Splits & Fragmentation: การแทรกข้อมูลแบบสุ่มคีย์ (เช่น Random GUID) เข้าไปในหน้าที่เต็มแล้ว จะทำให้เกิดการแบ่งหน้า (Page Split) ซึ่งลดประสิทธิภาพ I/O ลง

02 Subqueries & CTEs (Common Table Expressions)

เมื่อระบบเริ่มมีความซับซ้อน เช่น ต้องหา "ยอดขายของพนักงานที่สูงกว่าค่าเฉลี่ยของแผนกตนเอง" หรือ "การดึงแผนผังสายการบังคับบัญชาแบบลำดับชั้น" การเขียน SQL Query ให้สะอาด อ่านง่าย และประสิทธิภาพสูงถือเป็นทักษะชี้ขาดของ Senior Developer

Subquery คือคำสั่ง SELECT ที่ซ้อนอยู่ภายในคำสั่ง SQL หลัก แบ่งออกเป็น:
1. Scalar Subquery: คืนค่าแถวเดียวคอลัมน์เดียว
2. Correlated Subquery: Subquery ที่อ้างอิงค่าจาก Query ด้านนอก (ทำงานซ้ำทุกแถว อาจช้า)

📄Subquery-Examples.sql
-- ตัวอย่างที่ 1: Scalar Subquery ใน WHERE Clause
-- หาพนักงานที่มีเงินเดือนสูงกว่า "เงินเดือนเฉลี่ยของทั้งบริษัท"
SELECT EmployeeId, FirstName, LastName, Salary
FROM Employees
WHERE Salary > (SELECT AVG(Salary) FROM Employees);

-- ตัวอย่างที่ 2: Correlated Subquery
-- หาพนักงานที่มีเงินเดือนสูงกว่า "เงินเดือนเฉลี่ยของแผนกที่ตนเองสังกัด"
SELECT e.EmployeeId, e.FirstName, e.DepartmentId, e.Salary
FROM Employees e
WHERE e.Salary > (
    SELECT AVG(d.Salary) 
    FROM Employees d 
    WHERE d.DepartmentId = e.DepartmentId -- อ้างอิง e จากด้านนอก!
);

CTE (Common Table Expression) คือการสร้าง "ตารางผลลัพธ์ชั่วคราวที่มีชื่อ" (Named Temporary Result Set) โดยใช้คีย์เวิร์ด WITH ... AS (...) ทำให้โค้ดแบ่งเป็นสัดส่วน อ่านจากบนลงล่างได้เข้าใจง่ายกว่า Subquery ซ้อนหลายชั้น

📄CTE-Readable-Query.sql
-- การเขียน CTE หลายตารางพร้อมกันคั่นด้วยเครื่องหมายจุลภาค (,)
WITH DepartmentAverages AS (
    -- ขั้นตอนที่ 1: คำนวณเงินเดือนเฉลี่ยของแต่ละแผนก
    SELECT DepartmentId, AVG(Salary) AS AvgSalary
    FROM Employees
    GROUP BY DepartmentId
),
HighSalaryEmployees AS (
    -- ขั้นตอนที่ 2: กรองเฉพาะพนักงานที่เงินเดือนเกิน 50,000
    SELECT EmployeeId, FirstName, LastName, DepartmentId, Salary
    FROM Employees
    WHERE Salary >= 50000
)
-- ขั้นตอนที่ 3: รวมผลลัพธ์หลัก (Main Query)
SELECT 
    h.EmployeeId,
    h.FirstName + ' ' + h.LastName AS FullName,
    h.Salary,
    d.AvgSalary AS DepartmentAverage,
    h.Salary - d.AvgSalary AS DifferenceFromAvg
FROM HighSalaryEmployees h
INNER JOIN DepartmentAverages d ON h.DepartmentId = d.DepartmentId
ORDER BY DifferenceFromAvg DESC;

Recursive CTE ใช้สำหรับดึงข้อมูลที่มีความสัมพันธ์แบบลำดับชั้น (Hierarchy / Tree Structure) เช่น ผังโครงสร้างองค์กร (Org Chart), หมวดหมู่สินค้าย่อยไม่จำกัดระดับ โดยมี 2 ส่วนหลักคือ Anchor Member (จุดเริ่มต้น) และ Recursive Member (ส่วนเรียกตัวเอง)

📄Recursive-CTE-OrgChart.sql
-- ดึงสายการบังคับบัญชาตั้งแต่ CEO ลงมาจนถึงพนักงานระดับปฏิบัติการ
WITH OrgChartHierarchy AS (
    -- 1. Anchor Member: จุดเริ่มต้น (เช่น CEO ที่ไม่มี Manager / ManagerId IS NULL)
    SELECT 
        EmployeeId, 
        FirstName + ' ' + LastName AS EmployeeName, 
        ManagerId, 
        0 AS HierarchyLevel,
        CAST(FirstName + ' ' + LastName AS VARCHAR(MAX)) AS ReportingPath
    FROM Employees
    WHERE ManagerId IS NULL

    UNION ALL

    -- 2. Recursive Member: ดึงลูกน้องที่ขึ้นตรงกับคนที่พบในระดับก่อนหน้า
    SELECT 
        e.EmployeeId, 
        e.FirstName + ' ' + e.LastName AS EmployeeName, 
        e.ManagerId, 
        h.HierarchyLevel + 1,
        h.ReportingPath + ' -> ' + (e.FirstName + ' ' + e.LastName)
    FROM Employees e
    INNER JOIN OrgChartHierarchy h ON e.ManagerId = h.EmployeeId
)
SELECT 
    REPLICATE('    ', HierarchyLevel) + EmployeeName AS HierarchyTree,
    HierarchyLevel,
    ReportingPath
FROM OrgChartHierarchy
ORDER BY ReportingPath;

หนึ่งใน Pattern ที่ใช้บ่อยที่สุดในระดับ Enterprise คือการใช้ ROW_NUMBER() หรือ DENSE_RANK() ร่วมกับ CTE เพื่อทำ Pagination หรือหา Top N ต่อแต่ละกลุ่ม

📄TopN-Per-Group-Pagination.sql
-- โจทย์: หา "พนักงานที่ได้รับเงินเดือนสูงสุด 2 อันดับแรกของแต่ละแผนก"
WITH RankedSalaries AS (
    SELECT 
        EmployeeId,
        FirstName + ' ' + LastName AS FullName,
        DepartmentId,
        Salary,
        -- แบ่งกลุ่มตาม DepartmentId และจัดอันดับตาม Salary จากมากไปน้อย
        ROW_NUMBER() OVER (
            PARTITION BY DepartmentId 
            ORDER BY Salary DESC
        ) AS RowNum
    FROM Employees
)
SELECT 
    DepartmentId,
    RowNum AS DepartmentRank,
    FullName,
    Salary
FROM RankedSalaries
WHERE RowNum <= 2
ORDER BY DepartmentId, RowNum;

03 Database Transactions & ACID Properties

ความน่าเชื่อถือของฐานข้อมูลการเงินและระบบธุรกิจขนาดใหญ่ วางอยู่บนรากฐานที่เรียกว่า ACID Properties

A
Atomicity
(ความเป็นหนึ่งเดียว: All or Nothing)
ทุกคำสั่งย่อยใน Transaction ต้องสำเร็จครบทั้งหมด 100% หากมีคำสั่งใดล้มเหลวแม้แต่คำสั่งเดียว ทุกอย่างต้องถูก ROLLBACK ย้อนกลับสู่สถานะเดิม เหมือนไม่เคยมีอะไรเกิดขึ้น
C
Consistency
(ความถูกต้องตามกฎเกณฑ์)
ข้อมูลที่ถูกบันทึกต้องไม่ละเมิดกฎกติกาของฐานข้อมูล เช่น Foreign Key, Unique Constraints, Check Constraints และ Business Rules (เช่น ยอดคงเหลือห้ามติดลบ)
I
Isolation
(การแยกส่วนอิสระต่อกัน)
เมื่อมีผู้ใช้งานหรือ Transaction ทำงานพร้อมกันเป็นพันๆ รายการในเวลาเดียวกัน (Concurrency) แต่ละรายการต้องไม่เข้ามาก้าวก่ายหรืออ่านข้อมูลที่ยังแก้ไม่เสร็จของกันและกัน
D
Durability
(ความคงทนถาวร)
เมื่อ Transaction ได้รับการ COMMIT แล้ว ข้อมูลจะถูกบันทึกลงดิสก์และ Transaction Log (WAL) อย่างถาวร แม้ระบบจะไฟดับหรือเซิร์ฟเวอร์ระเบิดในวินาทีถัดไป ข้อมูลก็จะไม่สูญหาย

ระดับการล็อก (Transaction Isolation Levels)

ในระบบ RDBMS มีการแลกเปลี่ยน (Trade-off) ระหว่าง ความปลอดภัยของข้อมูล (Consistency) กับ ความเร็วในการทำงานพร้อมกัน (Concurrency Performance)

การเขียน T-SQL Transaction ระดับ Production ด้วย TRY...CATCH

โครงสร้างมาตรฐานในการเขียน Transaction ในระบบองค์กร ต้องมีบล็อก BEGIN TRY ... BEGIN CATCH และตรวจสอบ @@TRANCOUNT เสมอเพื่อความปลอดภัย

🛡️Robust-BankTransfer-Transaction.sql
-- ตัวอย่าง Stored Procedure การโอนเงินที่มี Transaction ปลอดภัย 100%
CREATE PROCEDURE dbo.sp_TransferMoney
    @FromAccountId INT,
    @ToAccountId INT,
    @Amount DECIMAL(18, 2)
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON; -- บังคับ Rollback อัตโนมัติหากเกิดข้อผิดพลาดร้ายแรง

    -- 1. ตรวจสอบเงื่อนไขเบื้องต้น (Validation)
    IF @Amount <= 0
    BEGIN
        RAISERROR('จำนวนเงินที่ต้องการโอนต้องมากกว่า 0 บาท', 16, 1);
        RETURN;
    END

    -- 2. เริ่มต้น Transaction
    BEGIN TRANSACTION;

    BEGIN TRY
        -- ตรวจสอบยอดเงินคงเหลือของผู้โอน
        DECLARE @CurrentBalance DECIMAL(18, 2);
        SELECT @CurrentBalance = Balance 
        FROM Accounts WITH (UPDLOCK, HOLDLOCK) -- ล็อกแถวป้องกัน Race Condition
        WHERE AccountId = @FromAccountId;

        IF @CurrentBalance < @Amount
        BEGIN
            -- เงินไม่พอ ให้ Raise Error เพื่อกระโดดไป CATCH
            THROW 50001, 'ยอดเงินคงเหลือในบัญชีต้นทางไม่เพียงพอสำหรับการโอน', 1;
        END

        -- ตัดเงินจากบัญชีต้นทาง
        UPDATE Accounts 
        SET Balance = Balance - @Amount, UpdatedDate = GETDATE()
        WHERE AccountId = @FromAccountId;

        -- เพิ่มเงินเข้าบัญชีปลายทาง
        UPDATE Accounts 
        SET Balance = Balance + @Amount, UpdatedDate = GETDATE()
        WHERE AccountId = @ToAccountId;

        -- บันทึกประวัติการทำธุรกรรม (Audit Log)
        INSERT INTO TransactionLogs (FromAccountId, ToAccountId, Amount, Status, CreatedDate)
        VALUES (@FromAccountId, @ToAccountId, @Amount, 'SUCCESS', GETDATE());

        -- หากทำงานครบถ้วนสมบูรณ์ ทำการ Commit
        COMMIT TRANSACTION;
        PRINT 'การโอนเงินจำนวน ' + CAST(@Amount AS VARCHAR) + ' บาท สำเร็จเรียบร้อย!';
    END TRY
    BEGIN CATCH
        -- 3. หากเกิดข้อผิดพลาด ให้ Rollback ทันที
        IF @@TRANCOUNT > 0
        BEGIN
            ROLLBACK TRANSACTION;
        END

        -- บันทึก Log ข้อผิดพลาด
        DECLARE @ErrorMessage NVARCHAR(4000) = ERROR_MESSAGE();
        DECLARE @ErrorSeverity INT = ERROR_SEVERITY();
        DECLARE @ErrorState INT = ERROR_STATE();

        PRINT 'เกิดข้อผิดพลาด! ทำการ Rollback ข้อมูลเรียบร้อย: ' + @ErrorMessage;
        
        -- ส่งต่อ Error ไปยัง Application Layer (เช่น .NET Web API)
        THROW @ErrorSeverity, @ErrorMessage, @ErrorState;
    END CATCH
END;

04 Stored Procedures, Functions & Views

ในฐานข้อมูลขนาดใหญ่ การจัดการ Logic จะถูกแบ่งออกเป็น 3 เครื่องมือหลักตามวัตถุประสงค์การใช้งาน

⚙️
Stored Procedures (SP)
ชุดคำสั่งประมวลผลทางธุรกิจ
- คอมไพล์ Execution Plan ล่วงหน้าในหน่วยความจำ
- รองรับคำสั่ง INSERT, UPDATE, DELETE, และ Transactions
- มี Input/Output Parameters และ Return Code
- ช่วยลด Network Traffic ระหว่าง App กับ Database
- ไม่สามารถ เรียกใช้ภายในคำสั่ง SELECT ... FROM SP ได้โดยตรง
📐
User-Defined Functions (UDF)
สูตรคำนวณและฟังก์ชันส่งค่ากลับ
- ต้องมีคำสั่ง RETURN เสมอ (Scalar หรือ Table-Valued)
- ห้ามแก้ไขข้อมูล (ห้าม INSERT/UPDATE ในตารางอื่น)
- สามารถนำไปเรียกใช้ใน SELECT, WHERE, และ JOIN ได้
- ⚠️ คำเตือน: Scalar UDFs ใน WHERE อาจทำให้เกิด RBAR (Row-By-Row) ทำให้ Query ช้าลงมหาศาล
👁️
Views (ตารางเสมือน)
บันทึก Query ที่ใช้บ่อย
- ไม่ได้เก็บข้อมูลจริงบนดิสก์ เป็นเพียง Saved Query (ยกเว้น Indexed View)
- ช่วยซ่อนความซับซ้อนของการ JOIN หลายตาราง
- ช่วยจำกัดสิทธิ์การมองเห็น เช่น ซ่อนคอลัมน์เงินเดือน หรือรหัสผ่าน
- ไม่สามารถรับ Parameter เข้ามาโดยตรงได้

ตัวอย่างโค้ด T-SQL: SP vs Function vs View

📜Database-Objects-Comparison.sql
-- 1. การสร้าง View สำหรับแสดงรายงานพนักงานแบบปลอดภัย (ซ่อน Salary)
CREATE VIEW dbo.vw_PublicEmployeeDirectory AS
SELECT 
    e.EmployeeId,
    e.FirstName + ' ' + e.LastName AS FullName,
    e.Email,
    d.DepartmentName,
    e.Position
FROM Employees e
INNER JOIN Departments d ON e.DepartmentId = d.DepartmentId;

-- เรียกใช้งาน View เหมือนตารางปกติ:
SELECT * FROM dbo.vw_PublicEmployeeDirectory WHERE DepartmentName = 'IT';


-- 2. การสร้าง Inline Table-Valued Function (iTVF) ที่รับ Parameter
CREATE FUNCTION dbo.fn_GetEmployeesByMinSalary(@MinSalary DECIMAL(18,2))
RETURNS TABLE
AS
RETURN (
    SELECT EmployeeId, FirstName, LastName, Salary, DepartmentId
    FROM Employees
    WHERE Salary >= @MinSalary
);

-- เรียกใช้ Function ร่วมกับคำสั่ง SELECT:
SELECT * FROM dbo.fn_GetEmployeesByMinSalary(45000) WHERE DepartmentId = 1;


-- 3. การสร้าง Stored Procedure พร้อม Output Parameter
CREATE PROCEDURE dbo.sp_GetDepartmentStats
    @DeptId INT,
    @TotalEmployees INT OUTPUT,
    @AvgSalary DECIMAL(18,2) OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    
    SELECT 
        @TotalEmployees = COUNT(*),
        @AvgSalary = ISNULL(AVG(Salary), 0)
    FROM Employees
    WHERE DepartmentId = @DeptId;
END;

-- เรียกใช้งาน Stored Procedure ใน T-SQL:
DECLARE @Count INT, @Avg DECIMAL(18,2);
EXEC dbo.sp_GetDepartmentStats @DeptId = 1, @TotalEmployees = @Count OUTPUT, @AvgSalary = @Avg OUTPUT;
SELECT @Count AS TotalStaff, @Avg AS AverageSalary;
