1. BOLA / IDOR (Insecure Direct Object Reference)

กลไกการโจมตี: แฮกเกอร์ Login ด้วย User A แล้วเปลี่ยน /api/orders/105 เป็น /api/orders/106 เพื่อแอบดูข้อมูลของ User B โดยที่ API Controller ไม่ได้เช็คว่าใครเป็นเจ้าของ Order นั้น

🛡️ SecureOrderService.cs (โค้ดป้องกันระดับ Database-First)
// 🛡️ การป้องกันที่ปลอดภัย 100%: ดึง UserId จาก Claims เสมอ
public async Task<OrderDto?> GetOrderByIdAsync(int orderId, int currentUserId)
{
    return await _context.Orders
        .AsNoTracking()
        .Where(o => o.Id == orderId && o.UserId == currentUserId) // 👈 Database-First Check
        .Select(o => new OrderDto(o.Id, o.TotalAmount, o.CreatedAt))
        .FirstOrDefaultAsync();
}

2. Financial Race Condition (Double-Spending)

กลไกการโจมตี: ยิง Request ถอนเงินพร้อมกัน 10 ครั้งใน 1 มิลลิวินาที ทำให้ทั้ง 10 Requests อ่านยอดเงินเดิมก่อนที่ยอดจะถูกตัด ส่งผลให้ถอนเงินเกินบัญชี

🔒 DatabaseLock.sql (การล็อกระดับแถวข้อมูลป้องกัน Race Condition)
-- 🔒 ใช้ Pessimistic Lock (UPDLOCK, HOLDLOCK) ใน Transaction
BEGIN TRANSACTION;

SELECT Balance 
FROM Accounts WITH (UPDLOCK, HOLDLOCK)
WHERE AccountId = @AccountId;

-- ตัดยอดเงินอย่างปลอดภัย ไม่สามารถเกิด Double-Spending ได้
UPDATE Accounts
SET Balance = Balance - @Amount
WHERE AccountId = @AccountId;

COMMIT TRANSACTION;

# 🛡️ รายงานแจ้งเตือนช่องโหว่ความปลอดภัยระดับวิกฤต (Confidential Security Assessment)

**เรียน:** คณะกรรมการบริหารความมั่นคงปลอดภัยสารสนเทศ (CISO / CTO)
**ผู้รายงาน:** วิศวกรความปลอดภัยสายขาว (White-Hat Security Engineer)
**ระดับความรุนแรง:** 🔴 High (CVSS v3.1 Score: 8.5)

---

## 1. บทสรุปสำหรับผู้บริหาร (Executive Summary)
ทีมตรวจพบช่องโหว่ประเภท **Broken Object Level Authorization (IDOR)** บนระบบ Web API ฝ่ายขาย ซึ่งอาจส่งผลกระทบให้บุคคลภายนอกสามารถเข้าถึงข้อมูลใบสั่งซื้อของลูกค้ารายอื่นได้โดยไม่ได้รับอนุญาต

## 2. ผลกระทบทางธุรกิจ (Business Impact)
- ⚠️ ความเสี่ยงต่อการรั่วไหลของข้อมูลส่วนบุคคล (PDPA Compliance Violation)
- ⚠️ ความเสียหายต่อภาพลักษณ์และความเชื่อมั่นขององค์กร

## 3. ขั้นตอนการพิสูจน์ช่องโหว่ (Proof of Concept - PoC)
1. ส่งคำขอ `GET /api/v1/orders/100` ด้วย Session ของ User A
2. แก้ไขพารามิเตอร์เป็น `GET /api/v1/orders/101` (ของ User B)
3. ระบบส่งข้อมูลใบสั่งซื้อกลับมาโดยไม่มีการตรวจสอบสิทธิ์ความเป็นเจ้าของ

## 4. ข้อเสนอแนะและแนวทางแก้ไข (Remediation Plan)
- บังคับใช้การตรวจสอบ Claims Identity ใน Application Layer
- บังคับใช้ Database Row-Level Security (RLS) กรอง `UserId == CurrentUserId` เสมอ

🛡️ โค้ดลับที่ 1: Automated Security Vulnerability Auditor (C# Tool)

เครื่องมือ C# สำหรับรันสแกนหาช่องโหว่ IDOR บน API Endpoint ขององค์กรคุณแบบอัตโนมัติ:

⚡ IdorVulnerabilityScanner.cs
using System;
using System.Net.Http;
using System.Net.Http.Headers;
using System.Threading.Tasks;

public class IdorVulnerabilityScanner
{
    private readonly HttpClient _client = new HttpClient();

    public async Task AuditEndpointAsync(string baseUrl, string userToken, int victimId)
    {
        Console.WriteLine($"🔍 กำลังเริ่มการสแกนความปลอดภัยสายขาวที่: {baseUrl}...");
        
        _client.DefaultRequestHeaders.Authorization = 
            new AuthenticationHeaderValue("Bearer", userToken);

        var response = await _client.GetAsync($"{baseUrl}/{victimId}");
        
        if (response.IsSuccessStatusCode)
        {
            Console.ForegroundColor = ConsoleColor.Red;
            Console.WriteLine($"🚨 [VULNERABILITY FOUND] ตรวจพบช่องโหว่ IDOR! ผู้ใช้สามารถเข้าถึงข้อมูล ID: {victimId} ได้!");
            Console.ResetColor();
        }
        else if (response.StatusCode == System.Net.HttpStatusCode.Forbidden || 
                 response.StatusCode == System.Net.HttpStatusCode.NotFound)
        {
            Console.ForegroundColor = ConsoleColor.Green;
            Console.WriteLine($"✅ [SECURE] ระบบปลอดภัย! ปฏิเสธการเข้าถึงข้อมูลข้ามบัญชีอย่างถูกต้อง ({response.StatusCode})");
            Console.ResetColor();
        }
    }
}
