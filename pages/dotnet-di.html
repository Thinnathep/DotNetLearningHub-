Dependency Injection (DI) ใน .NET

เจาะลึกระบบ Inversion of Control (IoC), เทคนิค Constructor Injection, 3 Service Lifetimes และการป้องกันปัญหา Captive Dependency
🎯 ระดับ: ⭐⭐ กลาง (Intermediate)
⏱️ เวลาเรียน: ~45 นาที
⚡ รางวัล: +100 XP
💻 รองรับ .NET 8 / .NET 9 (C# 12)

🚀 หัวใจสำคัญของการสร้าง Enterprise Application

ใน ASP.NET Core ระบบ Dependency Injection (DI) ไม่ใช่ฟีเจอร์เสริม แต่เป็นโครงสร้างพื้นฐานระดับ First-Class Citizen ที่ถูกฝังมาตั้งแต่เกิด ช่วยปลดล็อกโค้ดจากการผูกมัดแน่น (Tight Coupling) สู่ความยืดหยุ่นสูง (Loose Coupling) และทำให้การทดสอบด้วย Unit Test กลายเป็นเรื่องง่าย

💡
เปรียบเทียบให้เห็นภาพ (Analogy): ระบบโรงพยาบาลและห้องยา
เข้าใจ Inversion of Control และ DI ผ่านชีวิตประจำวัน
🏥 ชีวิตจริง vs Dependency Injection

ลองจินตนาการว่า หากคนไข้ป่วยแล้วต้อง "ออกไปหาพืชสมุนไพร บดสารเคมี และต้มยาเอง" นั่นคือการเขียนโค้ดแบบเดิมที่คลาสต้อง new ทุกอย่างเอง (Tight Coupling) ซึ่งอันตรายและพังง่ายมาก! แต่ในโรงพยาบาลยุคใหม่:

🤒
1. คนไข้ (Client / Controller)
Controller / Minimal API
ต้องการยาเพื่อรักษาอาการ ไม่จำเป็นต้องรู้วิธีผลิตยา แค่ระบุความต้องการผ่าน Constructor แล้วรอรับยาที่พร้อมใช้ไปทำงานต่อได้เลย
📋
2. ใบสั่งแพทย์ (Interface)
Interface เช่น IOrderService
สัญญามาตรฐาน (Contract) ระบุชื่อตัวยาและขนาดยา โดยไม่ผูกมัดกับยี่ห้อโรงงานผลิต เพื่อให้สามารถสลับเปลี่ยนยาเทียบเท่าได้ทันที
👨‍⚕️
3. เภสัชกร (DI Container)
IServiceProvider / IServiceCollection
ผู้ดูแลคลังยาและจัดยาตามใบสั่ง คอยควบคุมว่ายานี้ต้องจ่ายใหม่ทุกครั้ง (Transient), จ่ายเป็นชุดประจำเตียง (Scoped) หรือใช้ตู้ยาร่วมกันทั้งตึก (Singleton)
💊
4. ตัวยาจริง (Implementation)
Class เช่น OrderService
คลาสที่ลงมือประมวลผลการทำงานจริง (Concrete Class) ที่ถูกสร้างขึ้นและส่งมอบ (Inject) ให้แก่ผู้เรียกใช้งานอย่างปลอดภัย
01

ทำไมต้องใช้ DI? — จาก Tight Coupling สู่ Loose Coupling

แก้ปัญหาคำสั่ง new ที่ผูกมัดโค้ดจนยากแก่การบำรุงรักษาและทดสอบ

ในยุคก่อน เมื่อคลาส OrderService ต้องการบันทึกข้อมูลลงฐานข้อมูลและส่งอีเมลแจ้งเตือน เรามักเห็นโค้ดที่สร้าง Object ด้วยคำสั่ง new ภายในคลาสโดยตรง:

❌ ปัญหา: การผูกมัดแน่น (Tight Coupling — Bad Practice) 
public class OrderService
{
    private readonly SqlServerRepository _repository;
    private readonly SmtpEmailService _emailService;

    public OrderService()
    {
        // ❌ สร้าง Dependency เองโดยตรง (Tight Coupling)
        // ข้อเสีย 1: OrderService ถูกผูกติดกับ SQL Server และ SMTP Server ถาวร
        // ข้อเสีย 2: ไม่สามารถเขียน Unit Test ได้เลย เพราะจะไปต่อ Database จริงและส่ง Email จริง!
        // ข้อเสีย 3: ฝ่าฝืนหลัก Dependency Inversion Principle (DIP) ใน SOLID
        _repository = new SqlServerRepository("Server=prod-db;...");
        _emailService = new SmtpEmailService("smtp.office365.com", 587);
    }

    public async Task PlaceOrderAsync(Order order)
    {
        await _repository.SaveAsync(order);
        await _emailService.SendConfirmationAsync(order.CustomerEmail);
    }
}
⚠️ ทำไมคำสั่ง new ถึงสร้างหนี้ทางเทคนิค (Technical Debt)?
1. ยากต่อการเปลี่ยน Infrastructure: หากวันหนึ่งต้องการเปลี่ยนฐานข้อมูลจาก SQL Server เป็น PostgreSQL หรือ MongoDB คุณต้องแก้โค้ดทุกไฟล์ที่ new SqlServerRepository()
2. เขียน Automated Test ไม่ได้: เมื่อรัน Unit Test ระบบจะพยายามยิงเครือข่ายไปยัง SMTP และ DB จริง ทำให้ Test ช้า ไม่เสถียร และอาจทำลายข้อมูลจริงบน Production
3. จัดการ Lifecycle ของ Resource ไม่ได้: ไม่สามารถควบคุมได้ว่า Connection หรือ Instance ควรถูกแชร์หรือปิดทำลายเมื่อใด

ทางออกที่ถูกต้อง: ใช้หลักการ Inversion of Control (IoC) โดยย้ายความรับผิดชอบในการสร้าง Object ออกไปให้ DI Container และรับ Service เข้ามาผ่าน Constructor Injection:

✅ ทางออก: Loose Coupling ด้วย Dependency Injection (Good Practice) 
// 1. สร้าง Interface เพื่อเป็นตัวกลาง (Abstraction)
public interface IOrderRepository
{
    Task SaveAsync(Order order);
}

public interface IEmailService
{
    Task SendConfirmationAsync(string email);
}

// 2. ฉีด Interface เข้ามาทาง Constructor (Constructor Injection)
public class OrderService
{
    private readonly IOrderRepository _repository;
    private readonly IEmailService _emailService;

    // ✅ OrderService ไม่สนใจว่าใครเป็นผู้สร้าง หรือต่อกับ Database ตัวไหน
    // ขอเพียงส่ง Object ที่ปฏิบัติตาม Interface เข้ามาก็พร้อมทำงานทันที!
    public OrderService(IOrderRepository repository, IEmailService emailService)
    {
        _repository = repository;
        _emailService = emailService;
    }

    public async Task PlaceOrderAsync(Order order)
    {
        await _repository.SaveAsync(order);
        await _emailService.SendConfirmationAsync(order.CustomerEmail);
    }
}
💡 ประโยชน์เมื่อเขียน Unit Test ด้วย Mock
ในชุดทดสอบ Unit Test เราสามารถส่ง Mock<IOrderRepository> และ Mock<IEmailService> ปลอมๆ เข้าไปใน OrderService ได้ทันที ทำให้ทดสอบ Business Logic ได้ 100% ภายในเสี้ยววินาทีโดยไม่ต้องต่อ Database หรือ Network ใดๆ
02

3 Lifetimes ของ Service ใน ASP.NET Core

เข้าใจวงจรชีวิตของ Object เพื่อเลือกใช้อย่างถูกต้อง ไม่เปลือง Memory และไม่เกิด Concurrency Bug

เมื่อเราลงทะเบียน Service เข้าสู่ระบบของ ASP.NET Core ในไฟล์ Program.cs เราต้องระบุ Service Lifetime ซึ่งบอกให้ DI Container ทราบว่า "ควรสร้าง Instance บ่อยแค่ไหน และเมื่อใดควรทำลายทิ้ง" แบ่งออกเป็น 3 ระดับ ดังนี้:

⚡
Transient
AddTransient<T, U>()
🧻 เปรียบเหมือน: กระดาษทิชชู่
ดึงแผ่นใหม่ใช้ทุกครั้ง ใช้เสร็จทิ้งทันที ไม่แชร์ร่วมกับใคร
• การทำงาน: สร้าง Instance ใหม่ขึ้นมา ทุกครั้งที่มีการร้องขอ (Every Request for Injection) แม้จะอยู่ใน HTTP Request เดียวกันก็ตาม
• State: ไร้สถานะ (Stateless) ไม่เก็บข้อมูลค้างไว้
• เหมาะสำหรับ: บริการขนาดเล็กและทำงานรวดเร็ว (Lightweight) เช่น เครื่องคำนวณภาษี, แปลงสกุลเงิน, Token Generator
Stateless New Every Call Lightweight
🔄
Scoped
AddScoped<T, U>()
🍱 เปรียบเหมือน: ถาดอาหารประจำบุคคล
แต่ละคน (Request) ได้ถาดของตัวเอง วนใช้ตลอดมื้ออาหาร พออิ่มก็เก็บทิ้ง
• การทำงาน: สร้าง 1 Instance ต่อ 1 HTTP Request ทุก Class ที่ถูกเรียกใน Request เดียวกันจะได้ใช้ Instance ตัวเดียวกัน เมื่อจบ Request จะถูก Dispose ทันที
• State: เก็บสถานะเฉพาะภายใน 1 Request เท่านั้น
• เหมาะสำหรับ: DbContext (EF Core), Repository, Business Services, Unit of Work
1 Per HTTP Request DbContext Standard Auto Dispose
👑
Singleton
AddSingleton<T, U>()
🚰 เปรียบเหมือน: ตู้กดน้ำของสำนักงาน
ติดตั้งเครื่องเดียว ทุกคนในบริษัทและทุกคำขอเดินมากดใช้ตู้เดียวกันเสมอ
• การทำงาน: สร้าง เพียง 1 Instance ตลอดอายุของ Application ตั้งแต่เริ่มรันเซิร์ฟเวอร์จนกระทั่งปิดโปรแกรม ทุก HTTP Request และทุก Thread ใช้ร่วมกัน
• State: แชร์ข้อมูลร่วมกันทั้งระบบ (Global State)
• เหมาะสำหรับ: In-Memory Cache, Global Configuration, Logger, Background Task Worker
1 Per Application Memory Cache Must be Thread-Safe
🔍 ทำไม DbContext ใน Entity Framework Core จึงต้องเป็น Scoped เสมอ?
1. DbContext ไม่ใช่ Thread-Safe: หากใช้ Singleton และมี Request เข้ามาพร้อมกัน 10 คน จะเกิดการแย่งใช้งาน Connection เดียวกันจนแอป Crash ทันที
2. การทำงานแบบ Unit of Work: ใน 1 HTTP Request อาจมีการเรียกหลาย Service ทุก Service ควรเห็น Change Tracker ชุดเดียวกันเพื่อให้ SaveChangesAsync() บันทึกเป็น Transaction เดียวกันได้อย่างถูกต้อง
3. คืน Connection เข้า Pool ทันที: เมื่อ HTTP Request จบลง DI Container จะเรียก Dispose() ปิด Database Connection คืนสู่ Pool ป้องกัน Connection รั่วไหล (Leak)

📊 ตารางเปรียบเทียบ 3 Lifetimes อย่างละเอียด

เกณฑ์เปรียบเทียบ ⚡ Transient 🔄 Scoped (หัวใจหลักของ Web) 👑 Singleton
ความถี่การสร้าง Instance สร้างใหม่ทุกครั้งที่มีการ Inject หรือ GetService() สร้าง 1 ครั้งต่อ 1 HTTP Request (หรือ 1 Custom Scope) สร้างเพียงครั้งเดียวในครั้งแรกที่ถูกเรียก (หรือตอน App Start)
อายุการใช้งาน (Lifetime) สั้นมาก อยู่เท่ากับ Method หรือ Object ที่รับมันไป เท่ากับระยะเวลาประมวลผลของ HTTP Request นั้น ยาวนานเท่ากับ Application Lifecycle (จนสั่ง Stop Service)
การแชร์ข้อมูล (State Sharing) ไม่แชร์ข้อมูลใดๆ เลย (Isolated 100%) แชร์ข้อมูลข้าม Service ต่างๆ ภายใน Request เดียวกันได้ แชร์ข้อมูลให้กับทุก Request และทุกผู้ใช้งานในระบบ
ความปลอดภัยทาง Thread (Thread-Safety) ปลอดภัยสูง เพราะใช้งานแยก Instance กันโดยสิ้นเชิง ปลอดภัยตราบใดที่ 1 Request ถูกประมวลผลแบบ Single-thread ต้องระวังสูงมาก! โค้ดต้องเป็น Thread-safe เพราะถูกเรียกพร้อมกันได้
การใช้หน่วยความจำ (Memory) สร้างและทำลายบ่อย อาศัย Garbage Collector (GC) คืนหน่วยความจำทันทีเมื่อ Request สิ้นสุด กินหน่วยความจำค้างไว้ใน Heap ตลอดเวลาจนกว่าแอปจะปิด
ตัวอย่างคลาสที่เหมาะสม IEmailValidator, ITokenGenerator, IDateTimeProvider AppDbContext, IOrderRepository, IUserService IMemoryCache, IConfiguration, ILogger<T>
คำสั่งลงทะเบียนใน Program.cs builder.Services.AddTransient<...>(); builder.Services.AddScoped<...>(); builder.Services.AddSingleton<...>();
03

กับดักอันตราย — Captive Dependency

ข้อผิดพลาดร้ายแรงที่สุดในระบบ DI: การฉีด Scoped Service เข้าไปใน Singleton Service

🚨 Captive Dependency คืออะไร และทำไมจึงอันตรายถึงชีวิตของ Application?

Captive Dependency เกิดขึ้นเมื่อ Service ที่มีอายุขัยยาวนานกว่า (เช่น Singleton) รับ Service ที่มีอายุขัยสั้นกว่า (เช่น Scoped) เข้ามาทาง Constructor
เนื่องจาก Singleton จะถูกสร้างเพียงครั้งเดียวและคงอยู่ตลอดกาล ส่งผลให้ Scoped Service ตัวนั้น "ถูกกักขัง (Captured)" และมีอายุยืนยาวค้างฟ้าตาม Singleton ไปด้วยโดยที่ DI Container ไม่สามารถทำลายทิ้งได้เมื่อจบ HTTP Request!

💣 ตัวอย่างโค้ดที่เกิดปัญหา Captive Dependency (ห้ามทำเด็ดขาด!) 
// 1. AppDbContext ถูกลงทะเบียนเป็น Scoped ตามมาตรฐาน
builder.Services.AddDbContext<AppDbContext>();

// 2. แต่ NotificationQueue ถูกลงทะเบียนเป็น Singleton!
builder.Services.AddSingleton<INotificationQueue, NotificationQueue>();

// ❌ คลาสนี้เป็น Singleton แต่ฉีด AppDbContext (Scoped) เข้ามาใน Constructor!
public class NotificationQueue : INotificationQueue
{
    private readonly AppDbContext _db; // 💣 ถูกกักขังให้อยู่ตลอดไป (Captive)

    public NotificationQueue(AppDbContext db)
    {
        _db = db; // DbContext ตัวนี้จะไม่เคยถูก Dispose เลยตลอดอายุโปรแกรม!
    }

    public async Task ProcessQueueAsync()
    {
        // 💥 เมื่อมีหลาย Thread เรียกฟังก์ชันนี้พร้อมกัน
        // จะเกิด: InvalidOperationException: A second operation was started on this context instance before a previous operation completed.
        var users = await _db.Users.ToListAsync();
    }
}
💥 3 หายนะที่เกิดขึ้นเมื่อติดกับดัก Captive Dependency:
1. InvalidOperationException (Concurrency Crash): DbContext ตัวเดิมถูกหลาย Thread ใช้งานพร้อมกัน ทำให้แอปพังและส่ง HTTP 500 ให้ผู้ใช้งานทันที
2. Stale Data (ได้ข้อมูลเก่าที่ไม่อัปเดต): Change Tracker ของ DbContext ไม่เคยถูกล้าง ทำให้เมื่อมีข้อมูลอัปเดตใหม่ในฐานข้อมูล แอปยังคงอ่านได้ข้อมูลเดิมที่ค้างอยู่ใน Memory
3. Memory Leak มหาศาล: DbContext จะเก็บ Object ที่เคย Query ไว้ในหน่วยความจำตลอดไปจนกว่า Server จะเกิด Out Of Memory (OOM) และดับไป

🛠️ วิธีแก้ไขที่ถูกต้อง: การใช้ IServiceScopeFactory

หากเรามี Singleton Service (เช่น IHostedService, BackgroundService หรือ Worker) และจำเป็นต้องใช้งาน DbContext (Scoped) วิธีการที่ถูกต้องคือการฉีด IServiceScopeFactory แล้วสั่งสร้าง Scope ชั่วคราวเฉพาะตอนทำงาน:

✨ วิธีแก้: ใช้ IServiceScopeFactory เพื่อสร้าง Scope เฉพาะกิจ (Best Practice) 
public class QueueProcessorWorker : BackgroundService
{
    // ✅ 1. ฉีด IServiceScopeFactory (Singleton) เข้ามาอย่างปลอดภัย
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<QueueProcessorWorker> _logger;

    public QueueProcessorWorker(IServiceScopeFactory scopeFactory, ILogger<QueueProcessorWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            // ✅ 2. สร้าง Scope จำลองขึ้นมาใหม่สำหรับการประมวลผลรอบนี้
            using (var scope = _scopeFactory.CreateScope())
            {
                // ✅ 3. ดึง Scoped Service (AppDbContext) ออกมาจาก Scope เฉพาะกิจ
                var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

                var pendingTasks = await db.Queues.Where(q => !q.IsProcessed).ToListAsync(stoppingToken);
                
                foreach (var item in pendingTasks)
                {
                    item.IsProcessed = true;
                }

                await db.SaveChangesAsync(stoppingToken);
            } // ✅ 4. เมื่อหลุดบล็อก using: Scope และ AppDbContext จะถูก Dispose ทำลายทิ้งทันทีอย่างปลอดภัย!

            await Task.Delay(TimeSpan.FromSeconds(10), stoppingToken);
        }
    }
}
🛡️ ระบบตรวจจับอัตโนมัติของ .NET (ValidateScopes)
ในสภาพแวดล้อม Development (app.Environment.IsDevelopment()) ASP.NET Core จะเปิดการตรวจสอบ ValidateScopes = true และ ValidateOnBuild = true เป็นค่าเริ่มต้น โดยจะโยน Exception ทันทีที่สตาร์ทโปรแกรมหากตรวจพบว่ามีการฉีด Scoped Service เข้าไปใน Singleton Service เพื่อป้องกันไม่ให้บั๊กนี้หลุดไปถึง Production!
04

การลงทะเบียนและการฉีด Service ใน Controller & Minimal API

เรียนรู้วิธีตั้งค่า Program.cs และการเรียกใช้ Service ทั้งแบบ Controller แบบเดิมและ Minimal APIs ยุคใหม่

1. การลงทะเบียน Service ในไฟล์ Program.cs (.NET 8/9)

ในไฟล์ Program.cs เราจะใช้ builder.Services ในการกำหนดคู่ Interface และ Concrete Implementation ก่อนที่จะเรียกคำสั่ง builder.Build():

📄 Program.cs (Registration Examples) 
var builder = WebApplication.CreateBuilder(args);

// 1. ลงทะเบียนแบบ Transient
builder.Services.AddTransient<ITokenGenerator, JwtTokenGenerator>();

// 2. ลงทะเบียนแบบ Scoped (ใช้กับ Database & Business Logic)
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();
builder.Services.AddScoped<IOrderService, OrderService>();

// 3. ลงทะเบียนแบบ Singleton (ใช้กับ Cache หรือ Config)
builder.Services.AddSingleton<ICacheService, RedisCacheService>();

// 4. Keyed Services ใน .NET 8 (ระบุ Key ให้บริการที่มีหลาย Implementation)
builder.Services.AddKeyedScoped<INotificationService, EmailNotificationService>("email");
builder.Services.AddKeyedScoped<INotificationService, SmsNotificationService>("sms");

var app = builder.Build();

2. Constructor Injection ใน Controller (Classic Approach)

เมื่อต้องการใช้งาน Service ใน Controller ให้ประกาศตัวแปร private readonly และรับผ่านพารามิเตอร์ของ Constructor:

🎮 Controllers/OrdersController.cs 
[ApiController]
[Route("api/[controller]")]
public class OrdersController : ControllerBase
{
    private readonly IOrderService _orderService;
    private readonly ILogger<OrdersController> _logger;

    // ✅ DI Container จะส่ง OrderService และ Logger ตัวจริงเข้ามาให้อัตโนมัติ
    public OrdersController(IOrderService orderService, ILogger<OrdersController> logger)
    {
        _orderService = orderService;
        _logger = logger;
    }

    [HttpPost]
    public async Task<IActionResult> CreateOrder([FromBody] CreateOrderDto dto)
    {
        _logger.LogInformation("Creating order for customer {Email}", dto.CustomerEmail);
        var result = await _orderService.PlaceOrderAsync(dto);
        return CreatedAtAction(nameof(GetOrderById), new { id = result.Id }, result);
    }

    [HttpGet("{id}")]
    public async Task<IActionResult> GetOrderById(int id)
    {
        var order = await _orderService.GetByIdAsync(id);
        return order is not null ? Ok(order) : NotFound();
    }
}

3. Method Injection ใน Minimal APIs (.NET 8/9 Modern Approach)

ใน Minimal API ไม่จำเป็นต้องสร้าง Controller หรือเขียน Constructor! เราสามารถใส่ Service ที่ต้องการลงในพารามิเตอร์ของ Lambda Function ได้โดยตรง:

⚡ Program.cs (Minimal API Injection) 
// ✅ Direct Parameter Injection — ไม่ต้องเขียน [FromServices] ใน .NET 7/8/9
app.MapGet("/api/orders", async (IOrderService orderService) =>
{
    var orders = await orderService.GetAllOrdersAsync();
    return Results.Ok(orders);
});

// ✅ ใช้งานร่วมกับ DTO และ Service หลายตัวพร้อมกัน
app.MapPost("/api/orders", async (CreateOrderDto dto, IOrderService orderService, ILogger<Program> logger) =>
{
    logger.LogInformation("New Order Received from {Email}", dto.CustomerEmail);
    var newOrder = await orderService.PlaceOrderAsync(dto);
    return Results.Created($"/api/orders/{newOrder.Id}", newOrder);
});

// ✅ การใช้ [FromKeyedServices] ใน .NET 8 เพื่อเลือกตัวส่ง Notification
app.MapPost("/api/notify", async (string message, [FromKeyedServices("sms")] INotificationService notifier) =>
{
    await notifier.SendAsync("081-234-5678", message);
    return Results.Ok(new { status = "SMS Sent!" });
});

📋 กฎเหล็ก Best Practices สำหรับ Dependency Injection

✅ 1. พึ่งพา Abstraction เสมอ: ประกาศและ Inject ผ่าน Interface (เช่น IUserService) แทนที่จะเป็นคลาสจริงตรงๆ
✅ 2. หลีกเลี่ยง Service Locator Anti-pattern: ห้ามเรียกใช้ serviceProvider.GetService<T>() กระจายอยู่ในโค้ด เพราะทำให้ไม่รู้ว่าคลาสนั้นพึ่งพาอะไรบ้าง
✅ 3. Constructor ต้องกระชับ (Lean Constructor): Constructor มีหน้าที่รับและบันทึก Dependency ลงใน Field เท่านั้น ไม่ควรมีการต่อฐานข้อมูลหรือทำงานหนักๆ ใน Constructor
✅ 4. ตรวจสอบ Lifetimes ให้สอดคล้อง: ท่องจำเสมอ: Transient เรียกใครก็ได้, Scoped เรียก Scoped หรือ Singleton ได้, แต่ Singleton ห้ามฉีด Scoped Service เข้า Constructor ตรงๆ!
