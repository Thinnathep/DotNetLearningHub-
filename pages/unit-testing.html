Unit Testing ด้วย xUnit & Moq ใน .NET

คู่มือสมบูรณ์สำหรับเขียน Unit Test ระดับมืออาชีพ: เจาะลึก AAA Pattern, xUnit [Fact]/[Theory], เทคนิค Mocking ด้วย Moq, Test Naming Convention, Code Coverage และการขจัด Flaky Tests
🎯 ระดับ: ⭐⭐ กลาง
⏱️ เวลา: ~45 นาที
⚡ รางวัล: +100 XP
🏷️ หมวดหมู่: xUnit / Moq / Quality Assurance
🚗 เปรียบเทียบให้เห็นภาพ: ช่างตรวจเช็คสภาพเครื่องยนต์ก่อนส่งมอบรถยนต์
💡 ทำไมต้องมี Unit Test vs Integration Test?

ลองจินตนาการถึงโรงงานประกอบรถยนต์สมรรถนะสูง:

• 🧪 Unit Testing (การทดสอบระดับหน่วย): เหมือนกับช่างที่นำ "ลูกสูบแต่ละลูก" หรือ "หัวเทียนแต่ละอัน" มาจับขึ้นแท่นวัดขนาด แรงดัน และการจ่ายไฟเดี่ยวๆ ในห้องแล็บ โดยยังไม่ต้องประกอบเข้าตัวถังรถยนต์ เพื่อให้มั่นใจ 100% ว่าชิ้นส่วนชิ้นนี้ทำงานได้ตามสเปกเป๊ะทุกเงื่อนไข รันตรวจได้เป็นพันชิ้นในเสี้ยววินาที

• 🔩 Integration Testing (การทดสอบการทำงานร่วมกัน): คือการนำลูกสูบ เพลาข้อเหวี่ยง และเกียร์มาประกอบเข้าด้วยกัน แล้วสตาร์ทดูว่าส่งกำลังถึงกันได้ราบรื่นหรือไม่ (ทดสอบ Database, Message Queue หรือ External API จริง)

• 🏁 End-to-End Testing (การทดสอบทั้งระบบ): คือการขับรถคันจริงออกไปวิ่งบนถนนที่มีฝนตกและโค้งลาดชัน (ทดสอบ User Journey ผ่านหน้าบ้านและหลังบ้านจริง)

👑 E2E / UI Tests (5-10%)
ช้า, แพง, จำลอง User จริงทั้งระบบ
🔄 Integration Tests (15-20%)
เร็วปานกลาง, ต่อ Database จริง, ทดสอบเชื่อมโยง
⚡ Unit Tests (70-80% ของระบบ)
เร็วระดับมิลลิวินาที, ราคาถูกที่สุด, ทำงานแบบ Isolated 100%

01

รูปแบบ AAA Pattern (Arrange - Act - Assert) มาตรฐานสากล

โครงสร้าง 3 จังหวะที่เป็นมาตรฐานระดับโลกในการเขียน Unit Test ให้อ่านง่าย ตรวจสอบง่าย และบำรุงรักษาง่าย

1. ARRANGE (จัดเตรียม)

เตรียมข้อมูล & สถานะ

สร้างอ็อบเจกต์ (SUT - System Under Test), กำหนดค่า Input Parameter, จำลอง Mock Dependency และเซ็ตค่าเริ่มต้นที่จำเป็นก่อนเริ่มรัน

ตัวอย่าง: var cart = new ShoppingCart();
var item = new CartItem("Book", 500m);
2. ACT (กระทำ/สั่งการ)

เรียกใช้ Method จริง

สั่งรันฟังก์ชันหรือเมธอดที่ต้องการทดสอบเพียง 1 บรรทัด หรือ 1 Action หลัก เพื่อเก็บผลลัพธ์ (Result) หรือดักจับ Exception

ตัวอย่าง: cart.AddItem(item);
decimal total = cart.CalculateTotal();
3. ASSERT (ตรวจสอบผล)

ยืนยันความถูกต้อง

เปรียบเทียบผลลัพธ์ที่ได้ (Actual) กับสิ่งที่คาดหวังไว้ (Expected) โดยใช้ฟังก์ชันของ Assert.* หากไม่ตรง Test จะล้มเหลวทันที

ตัวอย่าง: Assert.Equal(500m, total);
Assert.Single(cart.Items);
📄 ShoppingCartTests.cs — ตัวอย่างโครงสร้าง AAA Pattern ครบวงจร 
using Xunit;
using MyStore.Core.Models;
using MyStore.Core.Services;

namespace MyStore.UnitTests.Services
{
    public class ShoppingCartTests
    {
        [Fact]
        public void CalculateTotal_WithValidDiscountCoupon_ReturnsDiscountedPrice()
        {
            // ─── 1. ARRANGE (จัดเตรียมข้อมูลและสถานะ) ───
            var cart = new ShoppingCart();
            cart.AddItem(new CartItem(id: 1, name: "Mechanical Keyboard", price: 3000m, quantity: 1));
            cart.AddItem(new CartItem(id: 2, name: "Wireless Mouse", price: 1000m, quantity: 1));
            
            var discountService = new DiscountCalculator();
            string couponCode = "DISCOUNT10"; // คูปองลด 10%

            // ─── 2. ACT (สั่งเรียก Method ที่ต้องการทดสอบจริง) ───
            decimal finalPrice = discountService.ApplyCoupon(cart, couponCode);

            // ─── 3. ASSERT (ตรวจสอบความถูกต้องของผลลัพธ์) ───
            // ราคารวม 4,000 บาท หักส่วนลด 10% (400) จะต้องเหลือ 3,600 บาท พอดี
            Assert.Equal(3600m, finalPrice);
            Assert.NotNull(cart.AppliedCoupon);
            Assert.True(cart.IsDiscountApplied);
        }

        [Fact]
        public void ApplyCoupon_WhenCouponIsExpired_ThrowsInvalidOperationException()
        {
            // ─── 1. ARRANGE ───
            var cart = new ShoppingCart();
            cart.AddItem(new CartItem(1, "USB Hub", 500m, 1));
            var discountService = new DiscountCalculator();
            string expiredCoupon = "EXPIRED2023";

            // ─── 2. ACT & 3. ASSERT (ตรวจสอบ Exception ด้วย Assert.Throws) ───
            var exception = Assert.Throws(() =>
            {
                discountService.ApplyCoupon(cart, expiredCoupon);
            });

            Assert.Equal("คูปองนี้หมดอายุการใช้งานแล้ว", exception.Message);
        }
    }
}
▶ Assert Methods สรุปการใช้งานที่พบบ่อยที่สุด: • Assert.Equal(expected, actual): ตรวจสอบว่าค่าสองตัวเท่ากันทุกประการ • Assert.NotEqual(notExpected, actual): ตรวจสอบว่าค่าต้องไม่เท่ากัน • Assert.NotNull(object) / Assert.Null(object): ตรวจสอบสถานะการมีอยู่ของ Reference • Assert.True(condition) / Assert.False(condition): ตรวจสอบเงื่อนไข Boolean • Assert.Throws<TException>(() => act()): ตรวจสอบว่าโค้ดโยน Exception ชนิดที่ระบุออกมาจริง • Assert.Contains("word", fullText) / Assert.Contains(item, collection): ตรวจสอบว่ามีสมาชิกอยู่ในชุดข้อมูล • Assert.Empty(collection) / Assert.Single(collection): ตรวจสอบจำนวนสมาชิกใน Collection
02

โครงสร้างโปรเจกต์ทดสอบ xUnit และ [Fact] vs [Theory]

เรียนรู้วิธีเซ็ตอัป xUnit Project, การใช้งาน [Fact] สำหรับกรณีเดี่ยว และ [Theory] ร่วมกับ [InlineData] เพื่อทดสอบหลายเงื่อนไข

🛠️ คำสั่ง .NET CLI ในการสร้างโปรเจกต์ Test

💻 Terminal CLI Setup
# 1. สร้าง Solution หลัก
dotnet new sln -n MyStoreApp

# 2. สร้าง Class Library โปรเจกต์จริง
dotnet new classlib -n MyStore.Core -o src/MyStore.Core

# 3. สร้าง xUnit Test Project
dotnet new xunit -n MyStore.Core.Tests -o tests/MyStore.Core.Tests

# 4. เชื่อมโยง Project Reference ให้โปรเจกต์ทดสอบมองเห็นโปรเจกต์จริง
dotnet add tests/MyStore.Core.Tests reference src/MyStore.Core

# 5. เพิ่มแพ็กเกจ Moq สำหรับจำลอง Dependencies
dotnet add tests/MyStore.Core.Tests package Moq

# 6. สั่งรัน Unit Test ทั้งหมดใน Solution
dotnet test

📊 เปรียบเทียบ [Fact] vs [Theory]

คุณสมบัติ [Fact] [Theory]
ความหมาย การทดสอบเงื่อนไข "เดี่ยว" (Single Scenario) ที่ค่า Input ตายตัวเสมอ การทดสอบ "ทฤษฎี/ชุดข้อมูล" (Parameterized) ด้วย Logic เดียวกันแต่เปลี่ยน Input
การรับ Parameter ❌ เมธอดห้ามรับ Parameter ใดๆ (Parameterless) ✅ เมธอดต้องรับ Parameter ตามที่ส่งมาจาก Data Source
แหล่งข้อมูล (Data Attributes) ไม่ต้องระบุ Attribute เพิ่มเติม ใช้ร่วมกับ [InlineData], [MemberData], หรือ [ClassData]
ผลลัพธ์ใน Test Runner นับเป็น 1 Test Case นับแยกเป็น N Test Cases ตามจำนวนแถวของข้อมูลที่ป้อนเข้ามา
ตัวอย่างการใช้งาน ตรวจสอบ Constructor ว่าเซ็ตค่า Default ถูกต้องหรือไม่ คำนวณเกรด (คะแนน 80-100 ได้ 'A', 70-79 ได้ 'B', ติดลบโยน Exception)
📄 TaxCalculatorTests.cs — เปรียบเทียบ Fact และ Theory + InlineData 
using Xunit;
using MyStore.Core.Services;

namespace MyStore.UnitTests.Services
{
    public class TaxCalculatorTests
    {
        // ─── ตัวอย่าง [Fact]: ทดสอบกรณีเฉพาะเจาะจง 1 เคส ───
        [Fact]
        public void CalculateVat_StandardNetPrice_ReturnsSevenPercentVat()
        {
            // Arrange
            var calculator = new TaxCalculator();
            decimal netPrice = 1000m;

            // Act
            decimal vat = calculator.CalculateVat(netPrice);

            // Assert (VAT 7% ของ 1,000 คือ 70 บาท)
            Assert.Equal(70m, vat);
        }

        // ─── ตัวอย่าง [Theory]: ทดสอบชุดข้อมูลหลากหลายด้วย Logic เดียวกัน ───
        [Theory]
        [InlineData(0, 0)]          // ยอด 0 บาท -> ภาษี 0 บาท
        [InlineData(100, 7)]        // ยอด 100 บาท -> ภาษี 7 บาท
        [InlineData(500, 35)]       // ยอด 500 บาท -> ภาษี 35 บาท
        [InlineData(1000, 70)]      // ยอด 1,000 บาท -> ภาษี 70 บาท
        [InlineData(2500, 175)]     // ยอด 2,500 บาท -> ภาษี 175 บาท
        public void CalculateVat_VariousAmounts_ReturnsCorrectSevenPercent(decimal netPrice, decimal expectedVat)
        {
            // Arrange
            var calculator = new TaxCalculator();

            // Act
            decimal actualVat = calculator.CalculateVat(netPrice);

            // Assert
            Assert.Equal(expectedVat, actualVat);
        }

        // ─── ตัวอย่าง [Theory] ดักจับ Boundary Values & Invalid Inputs ───
        [Theory]
        [InlineData(-1)]
        [InlineData(-100)]
        [InlineData(-9999.99)]
        public void CalculateVat_NegativeAmount_ThrowsArgumentOutOfRangeException(decimal negativePrice)
        {
            // Arrange
            var calculator = new TaxCalculator();

            // Act & Assert
            Assert.Throws(() =>
            {
                calculator.CalculateVat(negativePrice);
            });
        }
    }
}
03

การ Mocking Dependencies ด้วย Moq Library

ทำไมต้อง Mock? เข้าใจ Test Doubles, การใช้ Setup(), ReturnsAsync(), It.IsAny<T>() และ Verify()

🎭 ทำไมเราถึง "ห้าม" ต่อ Database หรือ Third-party API จริงใน Unit Test?

Unit Test มีเป้าหมายเพื่อทดสอบ Business Logic ในคลาสนั้นๆ เพียงอย่างเดียว (Single Unit of Work) การต่อ Database จริงหรือยิง API ภายนอกจะทำให้เกิดปัญหาใหญ่ 4 ประการ:

⏱️ ช้ามาก (Slow Execution)

การเปิด Connection ต่อฐานข้อมูลใช้เวลา 50-500ms ต่อเคส หากระบบมี 1,000 Tests จะใช้เวลาหลายนาที แต่ถ้าใช้ Mock จะรันเสร็จใน 1-2 วินาที!

💣 ข้อมูลปนเปื้อน (Side Effects & Pollution)

การเขียน/ลบข้อมูลใน DB จริงอาจทำให้ Test รันตีกันเอง หรือมีข้อมูลขยะค้างในระบบ

💸 ค่าใช้จ่าย & ข้อจำกัด (Cost & Rate Limits)

ถ้า Unit Test ยิง Payment Gateway (Stripe) หรือ SMS OTP จริง จะทำให้เสียเงินและติด Rate Limit ได้

🎲 ขาดความแน่นอน (Non-Deterministic)

หาก Network หลุด หรือเซิร์ฟเวอร์ภายนอกล่ม Unit Test จะตก ทั้งๆ ที่โค้ด C# ของเราเขียนถูกต้อง 100%

🎭 ตระกูล Test Doubles (ตัวแทนจำลอง 5 ประเภท)

ในวงการ Software Testing เราเรียกอ็อบเจกต์ตัวแทนเหล่านี้รวมๆ ว่า "Test Doubles" (เหมือนสตันท์แมนเล่นแทนดารา):

1. Dummy 🧸

วัตถุตัวประกอบ ส่งเข้าไปให้ครบพารามิเตอร์ของ Constructor แต่ไม่เคยถูกเรียกใช้จริงใน Logic

2. Stub 🪵

ตัวคืนค่าตายตัว คืนค่า Hardcoded response ที่เตรียมไว้ล่วงหน้าเพื่อป้อนข้อมูลให้ Logic ทำงานต่อได้

3. Spy 🕵️

สายสืบ บันทึกประวัติว่าฟังก์ชันถูกเรียกไปกี่ครั้ง ด้วย Parameter อะไรบ้าง เพื่อนำมา Assert ทีหลัง

4. Mock 🎭

ตัวเก่งสุด กำหนด Expectation และสามารถ Verify ตรวจสอบได้ว่าถูกเรียกตามเงื่อนไขที่กำหนดหรือไม่

5. Fake 🃏

มีโค้ดทำงานได้จริงแต่เป็นเวอร์ชันย่อส่วน เช่น In-Memory Database หรือ List ใน RAM แทน SQL Server

📄 OrderServiceTests.cs — การใช้งาน Moq แบบสมบูรณ์ใน Clean Architecture 
using System.Threading.Tasks;
using Xunit;
using Moq;
using MyStore.Core.Entities;
using MyStore.Core.Interfaces;
using MyStore.Core.Services;

namespace MyStore.UnitTests.Services
{
    public class OrderServiceTests
    {
        private readonly Mock _mockOrderRepo;
        private readonly Mock _mockPaymentGateway;
        private readonly Mock _mockNotification;
        private readonly OrderService _orderService; // System Under Test (SUT)

        public OrderServiceTests()
        {
            // สร้าง Mock Object สำหรับทุก Dependency ที่ OrderService ต้องใช้
            _mockOrderRepo = new Mock();
            _mockPaymentGateway = new Mock();
            _mockNotification = new Mock();

            // ฉีด Mock.Object เข้าไปใน Constructor ของ Service จริง
            _orderService = new OrderService(
                _mockOrderRepo.Object,
                _mockPaymentGateway.Object,
                _mockNotification.Object
            );
        }

        [Fact]
        public async Task CheckoutAsync_PaymentSuccessful_SavesOrderAndSendsEmail()
        {
            // ─── 1. ARRANGE ───
            var customerId = 42;
            var orderAmount = 2500m;
            var fakeOrder = new Order { Id = 101, CustomerId = customerId, TotalAmount = orderAmount };

            // ตั้งค่า Mock 1: จำลองให้ PaymentGateway ตัดเงินสำเร็จ และคืนค่า TransactionId
            _mockPaymentGateway
                .Setup(p => p.ChargeAsync(customerId, orderAmount))
                .ReturnsAsync(new PaymentResult { IsSuccess = true, TransactionId = "TXN-998877" });

            // ตั้งค่า Mock 2: จำลองการบันทึกข้อมูลลง Repo แล้วคืนค่า Order ที่มี ID
            _mockOrderRepo
                .Setup(r => r.CreateOrderAsync(It.IsAny()))
                .ReturnsAsync(fakeOrder);

            // ─── 2. ACT ───
            var result = await _orderService.CheckoutAsync(customerId, orderAmount);

            // ─── 3. ASSERT & VERIFY ───
            // 3.1 ตรวจสอบผลลัพธ์ของ Service
            Assert.True(result.IsSuccess);
            Assert.Equal(101, result.OrderId);

            // 3.2 ตรวจสอบว่า OrderRepo.CreateOrderAsync ถูกเรียกใช้งาน "1 ครั้งถ้วน"
            _mockOrderRepo.Verify(r => r.CreateOrderAsync(It.Is(o => 
                o.CustomerId == customerId && o.TotalAmount == orderAmount)), Times.Once);

            // 3.3 ตรวจสอบว่า NotificationService.SendConfirmationEmailAsync ถูกเรียกส่งอีเมล 1 ครั้ง
            _mockNotification.Verify(n => n.SendConfirmationEmailAsync(customerId, "TXN-998877"), Times.Once);
        }

        [Fact]
        public async Task CheckoutAsync_PaymentFails_DoesNotSaveOrderAndDoesNotSendEmail()
        {
            // ─── 1. ARRANGE ───
            var customerId = 99;
            var orderAmount = 5000m;

            // จำลองกรณีที่บัตรเครดิตถูกปฏิเสธ (Payment Failed)
            _mockPaymentGateway
                .Setup(p => p.ChargeAsync(customerId, orderAmount))
                .ReturnsAsync(new PaymentResult { IsSuccess = false, ErrorMessage = "Insufficient Funds" });

            // ─── 2. ACT ───
            var result = await _orderService.CheckoutAsync(customerId, orderAmount);

            // ─── 3. ASSERT & VERIFY ───
            Assert.False(result.IsSuccess);
            Assert.Equal("Insufficient Funds", result.ErrorMessage);

            // ✅ กฎเหล็ก: เมื่อตัดเงินไม่ผ่าน ต้อง "ไม่เคย" บันทึก Order และ "ไม่เคย" ส่งอีเมลเด็ดขาด (Times.Never)
            _mockOrderRepo.Verify(r => r.CreateOrderAsync(It.IsAny()), Times.Never);
            _mockNotification.Verify(n => n.SendConfirmationEmailAsync(It.IsAny(), It.IsAny()), Times.Never);
        }
    }
}
💡 สรุปหัวใจสำคัญของ Moq: • mock.Setup(x => x.Method(It.IsAny<T>())).ReturnsAsync(val); — กำหนดให้เมื่อเรียก Method นี้ด้วยค่าชนิด T ให้คืนค่า val ออกไปทันที
• mock.Verify(x => x.Method(), Times.Once); — ยืนยันว่าเมธอดนี้ถูกเรียกตรงตามจำนวนครั้งที่คาดไว้ (Times.Once, Times.Never, Times.Exactly(n))
04

เทคนิคการตั้งชื่อ Test Method ให้สื่อความหมาย & กฎ F.I.R.S.T.

เปลี่ยนชื่อ Test จากความคลุมเครือให้กลายเป็นเอกสารคู่มือ (Living Documentation) ที่อ่านรู้เรื่องทันทีเมื่อรันตกใน CI/CD

🏷️ สูตรมาตรฐานสากล: MethodName_StateUnderTest_ExpectedBehavior

เมื่อ Unit Test เกิด Failure ในระบบ Automated CI/CD Pipeline สิ่งเดียวที่โปรแกรมเมอร์จะเห็นในหน้ารายงานคือ "ชื่อเมธอดของ Test" ดังนั้นชื่อ Test ที่ดีต้องบอกได้ทันทีว่า เกิดอะไรขึ้น ในสถานการณ์ไหน และคาดหวังอะไร โดยไม่ต้องเปิดอ่านโค้ดข้างใน:

❌ ชื่อที่ไม่ดี (Bad / Vague) ✅ ชื่อที่ดีตามมาตรฐาน (Clean & Descriptive)
Test1() หรือ CheckDiscount() CalculateDiscount_VipMember_ReturnsTenPercentDiscount()
TransferMoney() TransferFunds_InsufficientBalance_ThrowsInvalidOperationException()
GetProduct() GetProductById_NonExistingId_ReturnsNull()
TestLoginError() Authenticate_InvalidPasswordThreeTimes_LocksAccountForThirtyMinutes()

⭐ หลักการ F.I.R.S.T. ของ Unit Test ระดับพรีเมียม

กฎ 5 ประการที่นักพัฒนาซอฟต์แวร์ระดับโลกยึดถือในการเขียน Unit Test ให้มีคุณภาพสูงสุด:

F
Fast (รวดเร็ว)

รันได้หลักพันเคสในเสี้ยววินาที เพื่อให้นักพัฒนารันได้บ่อยๆ ระหว่างเขียนโค้ด

I
Independent (อิสระ)

แต่ละเคสไม่พึ่งพาผลลัพธ์ของเคสก่อนหน้า สามารถสลับลำดับการรันได้อิสระ

R
Repeatable (รันซ้ำได้)

รันในเครื่องไหน เวลาใด สภาพแวดล้อมใด จะต้องได้ผลลัพธ์เดิม 100% เสมอ

S
Self-Validating (ตรวจตัวเอง)

ให้ผลลัพธ์แบบ Boolean คือ Pass หรือ Fail ชัดเจน ไม่ต้องให้คนมาคอยส่อง Log

T
Timely (ทันท่วงที)

เขียนพร้อมกันหรือเขียนก่อนโค้ดจริง (TDD - Test Driven Development)

05

Code Coverage & การป้องกัน Flaky Tests

วัดความครอบคลุมของการทดสอบอย่างถูกต้อง และกำจัดแบบทดสอบผีเข้าผีออก (Flaky Tests) ที่ทำลายความน่าเชื่อถือของ CI/CD

📈 Code Coverage คืออะไร?

ตัวชี้วัดเปอร์เซ็นต์ของซอร์สโค้ดที่ถูก Execute ในระหว่างการรันชุดแบบทดสอบ แบ่งเป็น:

  • Line Coverage: บรรทัดของโค้ดถูกรันผ่านหรือไม่
  • Branch Coverage: เงื่อนไข if / else / switch ทุกกิ่งก้าน (True/False) ถูกทดสอบครบหรือไม่
⚠️ กับดัก 100% Coverage: เปอร์เซ็นต์สูงไม่ได้การันตีว่าไม่มีบั๊ก! หากเขียน Test รันผ่านทุกบรรทัดแต่ไม่มีคำสั่ง Assert ตรวจสอบค่าที่ถูกต้อง ดังนั้นเป้าหมายที่ดีขององค์กรชั้นนำมักอยู่ที่ 75% - 85% Branch Coverage

👻 Flaky Tests คืออะไร?

แบบทดสอบที่ "เดี๋ยวผ่าน เดี๋ยวตก" โดยที่ไม่มีการแก้ไขซอร์สโค้ดเลยแม้แต่บรรทัดเดียว เป็นศัตรูอันดับ 1 ของทีมพัฒนาเพราะทำให้สูญเสียความไว้วางใจใน Build Pipeline

5 สาเหตุหลักของ Flaky Tests & วิธีแก้:

1. ผูกกับเวลาจริง (DateTime.Now): ใช้ TimeProvider (.NET 8) หรือ Mock IDateTime แทน
2. ใช้ Thread.Sleep() ใน Async: ให้ใช้ TaskCompletionSource หรือ Task-based mocking
3. แชร์ State ระหว่าง Tests: หลีกเลี่ยง Static Field ให้ new instance ใหม่ทุกเคส
4. ลำดับการรัน (Order Dependency): แต่ละ Test ต้องทำงานได้เดี่ยวๆ โดยไม่สนลำดับ
5. สุ่มข้อมูลโดยไม่คุม Edge Case: ใช้ Deterministic seed สำหรับ Random Generator
📊 คำสั่งสร้าง HTML Code Coverage Report แบบละเอียด
# 1. ติดตั้ง ReportGenerator Global Tool
dotnet tool install -g dotnet-reportgenerator-globaltool

# 2. รัน Test พร้อมเก็บค่า Code Coverage
dotnet test --collect:"XPlat Code Coverage"

# 3. แปลงไฟล์ coverage.cobertura.xml เป็น HTML Dashboard สวยงาม
reportgenerator \
  -reports:"**/TestResults/**/coverage.cobertura.xml" \
  -targetdir:"coveragereport" \
  -reporttypes:Html

# 4. เปิดดูรายงานผ่านเบราว์เซอร์
start coveragereport/index.html
