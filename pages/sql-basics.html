SQL พื้นฐานสำหรับ Backend .NET Developer

ทำความเข้าใจ Relational Database, เจาะลึกลำดับการประมวลผลจริงของ SQL Engine (Execution Order), คำสั่ง CRUD, การรวมตารางด้วย JOINs และ Aggregate Functions อย่างมั่นใจ
🎯 ระดับ: ⭐ พื้นฐาน
⏱️ เวลาเรียน: ~45 นาที
⚡ รางวัล: +100 XP
💾 รองรับ T-SQL / PostgreSQL / MySQL / SQLite
🏭
เปรียบเทียบให้เห็นภาพ: คลังสินค้าอัจฉริยะ (The Smart Warehouse Analogy)
ทำไมข้อมูลถึงต้องถูกจัดเรียงเป็นตาราง และเราคุยกับฐานข้อมูลอย่างไร?
💡 เปรียบเทียบเชิงสถาปัตยกรรม

ลองจินตนาการว่า Database (ฐานข้อมูล) คือโกดังสินค้าอัจฉริยะขนาดใหญ่ของบริษัท ที่มีหุ่นยนต์อัตโนมัติคอยวิ่งหยิบของให้เราตามคำสั่งภาษา SQL (Structured Query Language) ซึ่งเปรียบเสมือนใบเบิกสินค้าที่ระบุเงื่อนไขอย่างชัดเจน

🗄️
Table (ตาราง)
เช่น Products, Customers
ชั้นวางของแยกหมวดหมู่ ในโกดัง เช่น ชั้นวางสินค้าอิเล็กทรอนิกส์ หรือชั้นวางเฟอร์นิเจอร์ แต่ละชั้นจะเก็บของชนิดเดียวกันเท่านั้น
📦
Row / Record (แถว)
แถวข้อมูล 1 รายการ
กล่องสินค้าแต่ละชิ้น ที่วางอยู่บนชั้น วางเรียงกันทีละแถว แต่ละกล่องคือสินค้า 1 ชิ้นที่มีข้อมูลเฉพาะตัว
🏷️
Column / Field (คอลัมน์)
เช่น Price, StockQuantity
ป้ายสติกเกอร์บอกคุณสมบัติ ที่แปะอยู่ข้างกล่องสินค้าทุกใบ เช่น ป้ายรหัสสินค้า, ป้ายชื่อสินค้า, ป้ายราคา และวันหมดอายุ
🔑
Primary Key (PK)
คีย์หลักที่ไม่ซ้ำใคร
Serial Number / Barcode ประจำกล่อง ที่ไม่มีทางซ้ำกับกล่องใบไหนในโลก ใช้ระบุตัวตนของกล่องได้อย่างถูกต้อง 100% เสมอ
🔗
Foreign Key (FK)
คีย์นอกสำหรับเชื่อมโยง
ใบรายการสั่งซื้อที่อ้างอิงรหัสกล่อง เช่น ในใบสั่งซื้อ (Order) แปะรหัส CustomerId เพื่อบอกว่าของชิ้นนี้จะถูกส่งไปให้ลูกค้าคนใด
🤖
SQL Query Engine
ตัวประมวลผลคำสั่ง
หุ่นยนต์จัดการคลังสินค้า เมื่อคุณส่งโค้ด SQL มา หุ่นยนต์จะคำนวณเส้นทางหยิบของที่เร็วที่สุด (Execution Plan) แล้วนำผลลัพธ์มาส่งให้คุณ
01

ลำดับการประมวลผลจริงของคำสั่ง SQL (Order of Execution)

ความลับสำคัญที่สุดที่ Backend Developer ต้องเข้าใจ: ทำไมเราเขียน SELECT ก่อน แต่ฐานข้อมูลรัน SELECT ทีหลัง?

มือใหม่ส่วนใหญ่มักเข้าใจผิดว่า SQL Engine จะประมวลผลคำสั่งจาก บนลงล่าง ซ้ายไปขวา เหมือนภาษาโปรแกรมทั่วไป แต่ในความเป็นจริง SQL เป็นภาษาแบบ Declarative (เราบอกผลลัพธ์ที่ต้องการ ไม่ใช่ขั้นตอนทีละบรรทัด) ตัว Database Query Engine จะทำงานตามลำดับตรรกะภายในที่ต่างจากสิ่งที่เราเขียนอย่างสิ้นเชิง!

✍️ 1. ลำดับสิ่งที่เราเขียน (Lexical Syntax Order)

1. SELECT [DISTINCT] Columns, Expressions
2. FROM TableA JOIN TableB ON Condition
3. WHERE Row_Filters
4. GROUP BY Group_Columns
5. HAVING Group_Filters
6. ORDER BY Sort_Columns ASC|DESC
7. OFFSET / FETCH (LIMIT / TOP);

⚙️ 2. ลำดับที่ SQL Engine ประมวลผลจริง (Logical Execution Order)

1. FROM & JOIN     ➔ ค้นหาและจับคู่ตารางต้นทางเข้า Memory
2. WHERE           ➔ กรองแถวที่ไม่ต้องการทิ้งก่อนทันที
3. GROUP BY        ➔ จัดกลุ่มแถวที่เหลือเข้าด้วยกัน
4. HAVING          ➔ กรองกลุ่มที่ไม่ผ่านเกณฑ์ Aggregate ทิ้ง
5. SELECT          ➔ เลือกคอลัมน์ คำนวณนิพจน์ และสร้าง Alias
6. DISTINCT        ➔ ตัดแถวข้อมูลที่ผลลัพธ์ซ้ำกันออก
7. ORDER BY        ➔ จัดเรียงลำดับแถวผลลัพธ์
8. OFFSET / LIMIT  ➔ ตัดจำนวนแถวส่งกลับ (Pagination)

🎛️ Interactive Visualizer: จำลองขั้นตอนการทำงานของ SQL Engine

คลิกแต่ละขั้นตอนเพื่อดูการประมวลผลและการเปลี่ยนแปลงข้อมูลใน Memory

📍 ขั้นตอนที่ 1: FROM & JOIN (ระบุแหล่งข้อมูล)
Step 1 of 8
SQL Engine เริ่มต้นด้วยการระบุตารางต้นทางใน FROM หากมีการใช้ JOIN ฐานข้อมูลจะทำการจับคู่แถวข้อมูลตามเงื่อนไข ON เพื่อสร้างตารางผลลัพธ์ชั่วคราว (Working Table) ขึ้นมาใน Memory เพื่อใช้สำหรับขั้นตอนต่อไป
FROM Orders o INNER JOIN Customers c ON o.CustomerId = c.Id
💡 คำถามยอดฮิตสัมภาษณ์งาน: ทำไมเราถึงใช้ Column Alias ใน WHERE ไม่ได้?

สมมติคุณเขียน: SELECT Price * 0.9 AS DiscountPrice FROM Products WHERE DiscountPrice < 500
คำตอบ: จะเกิด Error ทันที! เพราะ WHERE ทำงานใน ขั้นตอนที่ 2 ในขณะที่ SELECT (ผู้ให้กำเนิดชื่อ DiscountPrice) ทำงานใน ขั้นตอนที่ 5 ในจังหวะที่ WHERE รัน Engine จึงยังไม่รู้จักชื่อ Alias นั้นเลย!

👉 แต่คุณสามารถใช้ DiscountPrice ใน ORDER BY (ขั้นตอนที่ 7) ได้ เพราะ ORDER BY ทำงานหลัง SELECT!

02

คำสั่ง CRUD พื้นฐาน (Create, Read, Update, Delete)

หัวใจหลักในการอ่าน เขียน แก้ไข และลบข้อมูลในฐานข้อมูลของ Backend API

1. READ — คำสั่ง SELECT และตัวกรอง WHERE

การค้นหาข้อมูลที่มีประสิทธิภาพขึ้นอยู่กับการเลือกคอลัมน์ที่จำเป็น (หลีกเลี่ยง SELECT * ในงานจริงบน Production) และการระบุเงื่อนไขด้วย WHERE ที่แม่นยำ:

📄 01_Select_Queries.sql 
-- 1. การเลือกเฉพาะคอลัมน์ที่ต้องการ (Best Practice)
SELECT Id, ProductName, UnitPrice, UnitsInStock
FROM Products;

-- 2. เงื่อนไขเปรียบเทียบตัวเลขและตรรกะ (AND, OR, NOT)
SELECT ProductName, UnitPrice, UnitsInStock
FROM Products
WHERE UnitPrice >= 500 AND UnitsInStock > 0;

-- 3. การใช้ IN สำหรับตรวจสอบค่าในกลุ่มที่กำหนด
SELECT Id, CustomerName, City
FROM Customers
WHERE City IN ('Bangkok', 'Chiang Mai', 'Phuket');

-- 4. การใช้ BETWEEN สำหรับช่วงข้อมูล (รวมหัวท้าย Inclusive)
SELECT OrderId, OrderDate, TotalAmount
FROM Orders
WHERE OrderDate BETWEEN '2026-01-01' AND '2026-06-30';

-- 5. การค้นหาข้อความด้วย LIKE (Pattern Matching)
-- % แทนตัวอักษร 0 ตัวขึ้นไป, _ แทนตัวอักษรใดๆ 1 ตัวพอดี
SELECT ProductName, Category
FROM Products
WHERE ProductName LIKE 'MacBook%'   -- ขึ้นต้นด้วย MacBook
   OR ProductName LIKE '%Pro%'      -- มีคำว่า Pro อยู่ตรงไหนก็ได้
   OR ProductName LIKE '_hone';     -- ลงท้ายด้วย hone มี 1 ตัวข้างหน้า เช่น Phone

-- 6. การตรวจสอบค่าว่าง NULL (ห้ามใช้ = NULL เด็ดขาด!)
SELECT CustomerId, CompanyName, Phone
FROM Customers
WHERE Phone IS NULL; -- หรือ IS NOT NULL

2. CREATE — คำสั่ง INSERT INTO (Single & Batch Insert)

การเพิ่มข้อมูลลงตาราง สามารถทำได้ทั้งแบบเพิ่มทีละแถว และการทำ Batch Multi-Row Insert เพื่อลด Round-trip Network I/O ระหว่าง .NET Application กับ SQL Server:

📄 02_Insert_Queries.sql 
-- แบบที่ 1: เพิ่มข้อมูลแถวเดียว (Single Row Insert)
INSERT INTO Categories (CategoryName, Description, IsActive)
VALUES ('Electronics', 'Smartphones, Laptops and Gadgets', 1);

-- แบบที่ 2: เพิ่มหลายแถวพร้อมกันในคำสั่งเดียว (Batch Insert - แนะนำมากสำหรับ Performance)
INSERT INTO Products (ProductName, CategoryId, UnitPrice, UnitsInStock)
VALUES 
    ('Dell XPS 15', 1, 65000.00, 10),
    ('Sony WH-1000XM5', 1, 13900.00, 25),
    ('iPad Pro 11"', 1, 32900.00, 18);

-- ใน SQL Server: การอ่านค่า Auto-Increment ID ที่เพิ่งถูก Insert ออกมาทันที
-- ใน C# Dapper หรือ ADO.NET นิยมใช้ SCOPE_IDENTITY() หรือ OUTPUT INSERTED.Id
INSERT INTO Customers (CustomerName, Email)
OUTPUT INSERTED.Id, INSERTED.CreatedAt
VALUES ('John Doe', 'john.doe@email.com');

3. UPDATE & DELETE — การแก้ไขและลบข้อมูล

🚨 กฎเหล็กข้อห้ามตาย: ห้ามรัน UPDATE หรือ DELETE โดยไม่มี WHERE เด็ดขาด!

หากคุณเผลอรัน UPDATE Products SET UnitPrice = 0; หรือ DELETE FROM Customers; โดยลืมใส่ WHERE ข้อมูล ทั้งตาราง จะถูกเขียนทับหรือลบหายเกลี้ยงทันทีในเสี้ยววินาที!

🛡️ วิถีความปลอดภัยของมืออาชีพ (Safe Execution Checklist):
  1. รัน SELECT ก่อนเสมอ: ก่อนจะ UPDATE/DELETE ให้เขียน SELECT * FROM ... WHERE [เงื่อนไข] ดูก่อนว่าจำนวนแถวที่โดนตรงกับที่เราตั้งใจหรือไม่
  2. ใช้ Transaction เสมอเวลาแมนนวล: ครอบด้วย BEGIN TRANSACTION; ตรวจสอบผลลัพธ์ ถ้าถูกต้องจึง COMMIT; ถ้าพลาดให้ ROLLBACK; ทันที
  3. ระบบ Production นิยม Soft Delete: อัปเดตแฟล็ก IsDeleted = 1 และ DeletedAt = GETUTCDATE() แทนการลบข้อมูลทิ้งจริง (Hard Delete)
📄 03_Update_Delete_Safe.sql 
-- ตัวอย่างการ UPDATE อย่างปลอดภัย
UPDATE Products
SET UnitPrice = UnitPrice * 1.05,  -- ปรับราคาขึ้น 5%
    UpdatedAt = GETUTCDATE()
WHERE CategoryId = 1 AND UnitsInStock > 0;

-- ตัวอย่างการทำ Safe Delete ด้วย Explicit Transaction ใน SQL Server
BEGIN TRANSACTION;

    -- ลบเฉพาะสินค้าที่ถูกยกเลิกการขายและไม่มีสต็อกเหลือ
    DELETE FROM Products
    WHERE IsDiscontinued = 1 AND UnitsInStock = 0;

    -- ตรวจสอบจำนวนแถวที่ได้รับผลกระทบ (Affected Rows)
    SELECT @@ROWCOUNT AS RowsDeleted;

-- หากจำนวนแถวถูกต้องให้รัน COMMIT; 
-- หากพบว่าลบผิดพลาดให้รัน ROLLBACK; ทันที
COMMIT TRANSACTION;
03

การรวมตารางด้วย SQL JOINs (Table Relationships)

หัวใจของ Relational Database — การดึงข้อมูลที่มีความสัมพันธ์กันจากหลายตารางมาประกอบร่างเป็นผลลัพธ์เดียว

ในระบบฐานข้อมูลเชิงสัมพันธ์ (RDBMS) ข้อมูลจะถูกแยกตารางเพื่อลดความซ้ำซ้อน (Database Normalization) เช่น แยกข้อมูล Customers (ลูกค้า) ออกจาก Orders (คำสั่งซื้อ) เมื่อเราต้องการดูว่า "ลูกค้าชื่ออะไร สั่งซื้อออเดอร์หมายเลขใดบ้าง" เราจึงต้องใช้ JOIN เชื่อมโยง Primary Key และ Foreign Key เข้าด้วยกัน

🧩 Interactive JOIN Visualizer: ทดลองคลิกเพื่อดูความแตกต่างของ JOIN แต่ละแบบ

ดูข้อมูลจำลองของตาราง Customers และ Orders ด้านล่าง แล้วสังเกตว่าผลลัพธ์เปลี่ยนไปอย่างไร

💡 INNER JOIN: ดึงเฉพาะลูกค้าที่ เคยมีประวัติการสั่งซื้อ (สมชายมี 2 ออเดอร์, สมหญิงมี 1 ออเดอร์) ส่วนวิชัยและกานดา (ไม่มีออเดอร์) และออเดอร์ 104 (ไม่มีลูกค้า) จะถูกตัดทิ้งทั้งหมด

📋 สรุปเปรียบเทียบประเภทของ SQL JOINs

ประเภท JOIN พฤติกรรมการดึงข้อมูล ตัวอย่าง Use Case ในงานจริง
INNER JOIN เอาเฉพาะแถวที่มีค่าเชื่อมโยง (Key) ตรงกันทั้งสองฝั่ง ตารางซ้ายและขวา ดึงใบเสร็จรับเงินที่ต้องมีข้อมูลทั้งลูกค้าและสินค้าครบถ้วน
LEFT JOIN เอา ตารางซ้ายมาทั้งหมด 100% หากตารางขวาไม่มีข้อมูลคู่ ให้เติมค่าเป็น NULL แสดงรายชื่อลูกค้าทั้งหมด และดูยอดซื้อ (ลูกค้าที่ไม่เคยซื้อจะได้ค่า NULL)
RIGHT JOIN เอา ตารางขวามาทั้งหมด 100% หากตารางซ้ายไม่มีข้อมูลคู่ ให้เติมค่าเป็น NULL คล้าย LEFT JOIN แต่มักเลี่ยงใช้โดยการสลับตารางมาอยู่ฝั่งซ้ายแทนเพื่อให้อ่านเข้าใจง่ายขึ้น
FULL OUTER JOIN เอา ทุกแถวของทั้งสองตาราง มารวมกัน แถวไหนจับคู่ไม่ได้ก็จะใส่ NULL การทำ Data Reconciliation ตรวจสอบความไม่สอดคล้องของข้อมูล 2 ฝั่ง
CROSS JOIN ผลคูณคาร์ทีเชียน (Cartesian Product) นำทุกแถวของ A มาจับคู่กับทุกแถวของ B ($M \times N$) การสร้างตาราง Matrix สินค้า x ไซส์เสื้อ x สี ทั้งหมดที่เป็นไปได้
04

Aggregate Functions & GROUP BY / HAVING

การคำนวณและสรุปสถิติข้อมูลชุดใหญ่ และความแตกต่างระหว่าง WHERE vs HAVING

ในระบบ Dashboard, Reporting หรือ Analytics หลังบ้านของ .NET เราต้องทำการสรุปผลตัวเลขสถิติ เช่น ยอดขายรวม ยอดสั่งซื้อเฉลี่ย หรือจำนวนสินค้าคงเหลือ ซึ่ง SQL มีฟังก์ชันคำนวณสรุปผล (Aggregate Functions) มาตรฐาน 5 ตัวหลัก:

COUNT()
นับจำนวนแถวข้อมูล

⚔️ ศึกแห่งความเข้าใจ: WHERE vs HAVING แตกต่างกันอย่างไร?

หัวข้อเปรียบเทียบ WHERE Clause HAVING Clause
ลำดับการทำงาน (Stage) ทำงานใน Step 2 (ก่อนการจัดกลุ่ม GROUP BY) ทำงานใน Step 4 (หลังจากการจัดกลุ่ม GROUP BY แล้ว)
เป้าหมายการกรอง (Target) กรองข้อมูลระดับ แถวเดี่ยว (Row-level filter) กรองข้อมูลระดับ กลุ่มผลลัพธ์รวม (Group-level filter)
การใช้ Aggregate Functions ❌ ห้ามใช้เด็ดขาด (เช่น WHERE SUM(Price) > 100 = Error) ✔️ ใช้งานได้โดยตรง (เช่น HAVING SUM(Price) > 100)
ประสิทธิภาพ (Performance) เร็วกว่ามาก เพราะตัดแถวทิ้งตั้งแต่ก่อนเอาเข้าหน่วยความจำ ช้ากว่าหากใช้กรองสิ่งที่ไม่ใช่ Aggregate เพราะต้องรัน Group ให้เสร็จก่อน

💻 ตัวอย่างคำสั่งจริง: วิเคราะห์ยอดขายรวมลูกค้าระดับ VIP

โจทย์: "ต้องการค้นหาลูกค้าที่อาศัยอยู่ในกรุงเทพฯ (Bangkok) ที่มียอดสั่งซื้อรวมเกิน 50,000 บาท และสั่งซื้ออย่างน้อย 2 ครั้ง โดยเรียงลำดับจากยอดซื้อรวมมากไปน้อย"

📄 04_Group_By_Having_VIP.sql 
SELECT 
    c.CustomerId,
    c.CustomerName,
    c.City,
    COUNT(o.OrderId) AS TotalOrders,
    SUM(o.TotalAmount) AS TotalSpending,
    AVG(o.TotalAmount) AS AverageBill
FROM Customers c
INNER JOIN Orders o ON c.CustomerId = o.CustomerId
WHERE c.City = 'Bangkok'                  -- 1. WHERE: กรองเอาเฉพาะลูกค้าในกรุงเทพฯ ก่อน Group
GROUP BY c.CustomerId, c.CustomerName, c.City -- 2. GROUP BY: จัดกลุ่มตามรหัสลูกค้า
HAVING SUM(o.TotalAmount) >= 50000        -- 3. HAVING: กรองเฉพาะกลุ่มที่ยอดซื้อรวม >= 50,000
   AND COUNT(o.OrderId) >= 2              --    และต้องมีออเดอร์ 2 ครั้งขึ้นไป
ORDER BY TotalSpending DESC;              -- 4. ORDER BY: เรียงลำดับยอดเงินรวมจากมากไปน้อย
QUERY RESULT OUTPUT:
CustomerId CustomerName City TotalOrders TotalSpending AverageBill
